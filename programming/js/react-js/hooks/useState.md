# React: `useState`

Усі виводи отримані реальним запуском: React 18.3.1 (`react-test-renderer`, `react-dom` + `jsdom`), якщо не сказано інше. Схема запуску — як у [../useEffect.md](../useEffect.md).

## 1. Що це

`useState` дає функціональному компоненту **пам'ять між рендерами**. Звичайна змінна `let n = 0` у тілі компонента скидається при кожному рендері (функція викликається заново). Стан, створений `useState`, **зберігає React** поза функцією, а зміна стану **запускає новий рендер** компонента.

```jsx
const [state, setState] = useState(initialValue);
```

- `state` — поточне значення (у цьому рендері);
- `setState` — функція, що **планує** оновлення й новий рендер;
- `initialValue` — початкове значення, **використовується лише при першому рендері**.

Для декількох значень викликають `useState` кілька разів — кожен виклик має свій «слот».

## 2. Як це виконується покроково

1. **Перший рендер (mount).** React викликає компонент. `useState(10)` створює слот зі значенням `10` і повертає `[10, setN]`.
2. Компонент повертає JSX. React малює DOM.
3. Користувач клікає → обробник викликає `setN(11)`. React **не змінює `n` у вже виконаній функції**; він записує «відкладене оновлення» у чергу слота і **планує рендер**.
4. **Повторний рендер.** React знову викликає компонент. Тепер `useState(10)` бачить, що слот уже існує, ігнорує `10` і повертає **поточне значення** `11`.
5. React порівнює новий JSX із попереднім і оновлює лише змінене в DOM.

Реальний вивід (початкове `10`, потім `setN(11)`, `setN(12)`): `render n= 10 | render n= 11 | render n= 12`.

Ключова ідея: **стан — це знімок (snapshot)**. У межах одного рендеру `n` — константа; код у цьому рендері бачить значення саме цього рендеру.

## 3. Лінива ініціалізація

`useState(expensive())` викликає `expensive()` **при кожному рендері** (результат ігнорується, але обчислення відбувається). Виміряно: за 3 рендери — **3** виклики.
`useState(() => expensive())` — функція виконується **лише один раз** (при першому рендері): **1** виклик.

```jsx
const [data] = useState(() => JSON.parse(localStorage.getItem("data")));
```
Функція-ініціалізатор має бути **чистою** і не приймати аргументів.

## 4. Оновлення на основі попереднього значення

```jsx
setCount(count + 1);       // використовує count з ЗНІМКА цього рендеру
setCount(c => c + 1);      // «функція-оновлювач»: отримує актуальне значення з черги
```
Виміряно: три виклики `setN(n + 1)` підряд (n = 0) дали `1` (усі бачили `n = 0`), а три `setN(x => x + 1)` — `4` (було 1, стало 4: **+3**).

Правило: якщо новий стан залежить від старого — використовуй функцію-оновлювач. Особливо в таймерах, асинхронному коді й кількох оновленнях підряд.

## 5. Пакетне оновлення (batching)

Кілька `setState` в одному обробнику → **один** рендер. Виміряно: `setA(1); setB(1)` → **1 рендер**. У React 18 (з `createRoot`) пакетування автоматичне й у `setTimeout`, промісах, нативних подіях: 2 виклики в одному «тіку» → **1 рендер**. Щоб форсувати синхронний рендер — `flushSync(() => setX(...))` (кожен окремо → **2 рендери**). Використовуй рідко.

## 6. Відмова від оновлення (bail-out)

React порівнює нове значення зі старим через `Object.is`. Якщо рівні — **рендеру немає** (виміряно: `setN(5)` при `n = 5` → **0** рендерів, двічі поспіль теж 0).

## 7. Незмінність (immutability)

Об'єкти й масиви потрібно **замінювати**, а не мутувати. Виміряно: `o.a = 2; setO(o)` (те саме посилання) → **0 рендерів**, UI показує старе `1`, хоча об'єкт змінений. `setO({ ...o, a: o.a + 1 })` → 1 рендер, UI оновився.

```jsx
setUser({ ...user, age: user.age + 1 });          // об'єкт
setItems([...items, newItem]);                    // додати
setItems(items.filter(i => i.id !== id));         // видалити
setItems(items.map(i => i.id === id ? { ...i, done: true } : i));  // змінити
```
Для глибоких структур — `structuredClone` або бібліотека Immer.

## 7a. Функція як значення стану

Якщо передати в `setState` функцію, React вважає її **оновлювачем** і викличе. Виміряно: `useState(() => () => 'A')` зберегло функцію; після `setF(() => 'B')` стан став **рядком `'B'`** (React викликав функцію й записав результат; `f()` зламалось: `not a function: B`). Щоб зберегти функцію у стані — обгорни: `setF(() => () => 'C')`.

## 8. Обробник бачить знімок свого рендеру

```jsx
function handle() { setN(n + 1); console.log(n); }   // лог покаже СТАРЕ n
```
Виміряно: після `setN(n + 1)` у тому ж обробнику `n` лишилось `0`. Нове значення з'явиться лише в наступному рендері. Те саме з `setTimeout`/`fetch`: замикання тримає `n` свого рендеру.

## 9. Скидання стану: `key` і розмонтування

Стан належить **позиції компонента в дереві**. Інший `key` → новий компонент із новим станом; видалення з дерева → стан втрачається. `<Form key={userId} />` — спосіб скинути форму при зміні користувача.

## 10. «Похідний» стан під час рендеру

Якщо стан має скинутись при зміні пропса, можна викликати `setState` **прямо під час рендеру** (не в ефекті) — React одразу повторить рендер без показу проміжного результату. Виміряно (`p` змінився `1 → 2`): UI стало `2:0`, **2 рендери**. Умова обов'язкова (`if (p !== prev)`), інакше нескінченний цикл. Зазвичай краще `key` або обчислення з пропсів без стану.

## 11. Strict Mode

У розробці (`<StrictMode>`) React викликає компонент і **ініціалізатор стану двічі** для виявлення нечистоти. Виміряно: `renders 2`, `lazy init calls 2`. У production — по одному. Тому ініціалізатори й тіло компонента мусять бути чистими.

## 12. `setState` після розмонтування

У React 18 більше не показується попередження «Can't perform a React state update on an unmounted component»; виклик просто нічого не робить (виміряно: без помилки).

## 13. Типові помилки

1. Мутувати стан (`state.push(x)`, `obj.a = 1`) замість заміни → UI не оновлюється.
2. `setCount(count + 1)` кілька разів підряд → лише +1; потрібен `c => c + 1`.
3. Очікувати нове значення одразу після `setState` у тому ж обробнику.
4. `useState(expensive())` замість `useState(() => expensive())`.
5. Зберігати у стані **похідні** дані (які можна обчислити з інших) → розсинхрон. Рахуй у рендері.
6. Класти у стан функцію без обгортки.
7. Викликати `setState` в тілі компонента без умови → нескінченний цикл «Too many re-renders».
8. Передавати початкове значення з пропса й чекати, що воно оновлюватиметься: `useState(props.x)` читає `props.x` лише **один раз**.
9. Зберігати в одному стані занадто багато — оновлення будь-якої частини перерендерує компонент; групуй логічно або використовуй `useReducer`.
10. Мутувати вкладений об'єкт через `{...state}` (копія лише першого рівня).

## 14. Алгоритм використання

1. Визнач, чи значення має **змінюватись і впливати на UI**. Ні → звичайна змінна/`useRef`.
2. Можна обчислити з інших стану/пропсів → **не** тримай у стані.
3. Початкове значення дороге → ліниво: `useState(() => ...)`.
4. Нове значення залежить від старого → `setX(prev => ...)`.
5. Об'єкти/масиви — завжди нове значення, ніколи мутація.
6. Складна логіка переходів → `useReducer`.
