# V8: стабільність типів (type stability) і мономорфізм

## Загальна ідея

V8 компілює функції спеціально під типи даних, які вона отримує. Якщо функція завжди отримує числа — генерується швидкий код для чисел. Якщо типи змінюються — V8 деоптимізує код і повертається до повільнішого шляху.

Основне правило: функція повинна обробляти один тип даних. Якщо типи різні — розділи на окремі функції або переконайся, що тип завжди однаковий (явно конвертуй на вході).

## 1. Три стадії компіляції V8

V8 не компілює код одразу. Він спостерігає, потім оптимізує:

- **Рівень 1: інтерпретатор (Ignition)** — виконує код напряму, без компіляції; повільно, але одразу готовий; збирає інформацію про типи.
- ↓ (якщо функція викликається часто)
- **Рівень 2: baseline compiler (Sparkplug)** — компілює в машинний код; швидко, але без глибоких оптимізацій.
- ↓ (якщо функція викликається дуже часто)
- **Рівень 3: optimizing compiler (TurboFan)** — компілює з максимальними оптимізаціями під конкретні типи; найшвидший можливий код.

Ключовий момент: TurboFan генерує код під конкретні типи, які він спостерігав. Якщо тип зміниться — код стає невалідним (деоптимізація).

## 2. Що відбувається на машинному рівні

```js
function add(a, b) {
  return a + b;
}
```

Якщо V8 бачить тільки числа (type stable) — ARM64 Assembly (TurboFan), `a` в `x0`, `b` в `x1`:

```asm
add x0, x0, x1   ; просте додавання
ret
; 2 інструкції, 1 такт процесора
```

Якщо V8 не знає тип (type unstable):

```asm
ldr x2, [x0]              ; завантаж тип a
cmp x2, #SMI_TAG          ; чи це ціле число?
bne .check_heap_number    ; якщо ні, перевір float
bne .check_string         ; якщо ні, перевір string
bne .generic_add          ; загальний шлях
.smi_add:
add x0, x0, x1
ret
.check_heap_number: ; ... ще 20+ інструкцій
.check_string:      ; ... ще 30+ інструкцій
.generic_add:       ; ... ще 50+ інструкцій, виклик runtime функції
```

Різниця: 2 інструкції проти 50–100 — потенційно на порядок повільніше (детально про регістри й асемблер ARM64 — нотатка `programming/assembly/arm64/arm64.md`).

## 3. Типи всередині V8

JavaScript має тип `"number"`, але V8 розрізняє більше варіантів:

- **SMI (Small Integer)** — цілі числа від −2³¹ до 2³¹−1 (наприклад, `1`, `42`, `-100`, `0`); зберігається прямо в pointer (без алокації на купі!) — найшвидший варіант.
- **HeapNumber (Double)** — числа з рухомою комою (наприклад, `3.14`, `1.5`, `-0.001`); зберігається на купі (повільніше).
- **BigInt** — дуже великі числа (наприклад, `9007199254740993n`) — найповільніший варіант для арифметики.

Навіть усередині `"number"` є різниця:

```js
add(1, 2);     // SMI + SMI       → найшвидший шлях
add(1.5, 2.5); // Double + Double → інший шлях
add(1, 2.5);   // SMI + Double    → мусить конвертувати
```

## 4. Monomorphic, polymorphic, megamorphic — три рівні стабільності типу

```js
function processValue(value) {
  return value * 2;
}
```

**Monomorphic (один тип) — ідеально:**

```js
processValue(1);    // SMI
processValue(2);    // SMI
processValue(100);  // SMI
// V8: "завжди SMI! компілюю super-fast code"
```

**Polymorphic (2–4 типи) — гірше:**

```js
processValue(1);    // SMI
processValue(1.5);  // HeapNumber
processValue(2);    // SMI
// V8: "бачив 2 різних типи, генерую код для обох"
```

**Megamorphic (5+ типів) — дуже погано:**

```js
processValue(1);        // SMI
processValue(1.5);      // HeapNumber
processValue("hello");  // String
processValue(true);     // Boolean
processValue({});       // Object
// V8: "не маю уявлення, що прийде — відключаю оптимізації"
```

Відносний порядок сповільнення (monomorphic → polymorphic → megamorphic) реальний і задокументований, але конкретні мілісекунди застарівають дуже швидко з кожною новою версією V8 — дивіться чесний вимір у розділі 7, а не орієнтуйтесь на конкретні числа з будь-якої статті, включно з цією.

## 5. Speculative optimization та деоптимізація

V8 робить «ставку» на тип на основі спостережень:

```js
function multiply(a, b) {
  return a * b;
}

// розігрів: V8 спостерігає
for (let i = 0; i < 100000; i++) {
  multiply(i, 2); // завжди SMI
}
```

TurboFan: «завжди числа! компілюю оптимізований код». Код містить guard (захист):

```text
GUARD: чи a — число? якщо ні → DEOPTIMIZE
GUARD: чи b — число? якщо ні → DEOPTIMIZE
result = a * b  (машинна інструкція)
```

```js
multiply("hello", 2); // ❌ guard не пройшов!
```

Що робить V8 при деоптимізації: зупиняє виконання оптимізованого коду → відтворює стан стека → продовжує в інтерпретаторі (значно повільніше) → збирає нову інформацію про типи → пробує скомпілювати знову (тепер для двох типів). Деоптимізація коштує помітних накладних витрат; якщо відбувається часто — це серйозна проблема для продуктивності.

Як побачити деоптимізацію:

```bash
node --trace-deopt myfile.js
```

Виведе щось на кшталт:

```text
[deoptimizing (DEOPT eager)]: begin 0x... multiply
translating frame multiply => node=3, height=24
```

## 6. Масиви та типи елементів

V8 відстежує типи елементів масиву окремо від типів звичайних властивостей:

```js
const arrSmi = [1, 2, 3, 4, 5];       // PACKED_SMI_ELEMENTS (найшвидше)
const arrDouble = [1.1, 2.2, 3.3];     // PACKED_DOUBLE_ELEMENTS
const arrMixed = [1, 2, "three", 4];   // PACKED_ELEMENTS (повільніше для числових операцій)
const arrHoley = [1, 2, , 4, 5];       // HOLEY_SMI_ELEMENTS (діри = повільніше)
```

Важливо: тип масиву може тільки «деградувати», назад повернутись не можна:

```js
const degradingArr = [1, 2, 3];       // PACKED_SMI_ELEMENTS
degradingArr.push(3.14);               // → PACKED_DOUBLE_ELEMENTS (деградація!)
degradingArr.push("hello");            // → PACKED_ELEMENTS (деградація!)
// назад до SMI вже неможливо, навіть якщо видалиш рядок!
```

## Правила для стабільності типів

### Правило 1: функція повинна отримувати один тип

```js
// ❌ Неправильно:
function formatBad(value) {
  return value.toString();
}
formatBad(42);
formatBad("hello");
formatBad(true);
```

```js
// ✅ Правильно: окремі функції для різних типів
function formatNumber(value) {
  return value.toString();
}
function formatString(value) {
  return value;
}
```

### Правило 2: явно конвертуй типи на вході

```js
// ❌ Неправильно: значення від API може бути string або number
async function processUserBad(userId) {
  const user = await fetchUserStub(userId);
  return user.age * 2; // "30" * 2 або 30 * 2?
}
```

```js
// ✅ Правильно: явна конвертація
async function processUser(userId) {
  const user = await fetchUserStub(userId);
  const age = Number(user.age); // завжди number
  return age * 2;
}
function fetchUserStub() {
  return Promise.resolve({ age: "30" }); // заглушка для прикладу
}
```

### Правило 3: уникай змішаних масивів

```js
// ❌ Неправильно:
const dataMixed = [1, 2, "3", 4, null, 6];
```

```js
// ✅ Правильно:
const numbersOnly = [1, 2, 3, 4, 5, 6];
const stringsOnly = ["1", "2", "3"];
```

### Правило 4: default-параметри замість «необов'язкових» типів

```js
// ❌ Неправильно: multiplier може бути number або undefined
function calculateBad(a, b, multiplier) {
  const m = multiplier || 1;
  return (a + b) * m;
}
calculateBad(1, 2);    // multiplier = undefined
calculateBad(1, 2, 3); // multiplier = number
```

```js
// ✅ Правильно: default-параметр → завжди number
function calculate(a, b, multiplier = 1) {
  return (a + b) * multiplier;
}
```

### Правило 5: уникай зміни типу елементів масиву

```js
// ❌ Неправильно:
const arrDegrade = [1, 2, 3]; // PACKED_SMI_ELEMENTS
arrDegrade.push(3.14);         // деградує до PACKED_DOUBLE_ELEMENTS
```

```js
// ✅ Правильно: визнач тип від початку
const arrStableFromStart = [1.0, 2.0, 3.0]; // одразу PACKED_DOUBLE_ELEMENTS
arrStableFromStart.push(3.14);               // залишається PACKED_DOUBLE_ELEMENTS
```

### Правило 6: TypeScript допомагає, але не гарантує

TypeScript перевіряє типи при компіляції:

```typescript
function add(a: number, b: number): number { return a + b; }
```

Але в рантаймі (наприклад, через `as any` чи зовнішні дані):

```typescript
const result = add(1 as any, "hello" as any);
// TypeScript: OK (через any)
// V8 в рантаймі: DEOPTIMIZE!
```

TypeScript допомагає тим, що ти сам не пишеш код з різними типами — але не захищає від зовнішніх (наприклад, мережевих) даних.

## 7. Вплив на продуктивність — чесний бенчмарк

```js
const { performance } = require("perf_hooks");

function stableAdd(a, b) {
  return a + b;
}
function unstableAdd(a, b) {
  return a + b;
}

// "забрудни" unstableAdd різними типами:
unstableAdd(1, 2);
unstableAdd(1.5, 2.5);
unstableAdd("a", "b");

let t0 = performance.now();
for (let i = 0; i < 100000000; i++) stableAdd(i, i + 1);
console.log(`Stable:   ${(performance.now() - t0).toFixed(0)}ms`);

t0 = performance.now();
for (let i = 0; i < 100000000; i++) unstableAdd(i, i + 1);
console.log(`Unstable: ${(performance.now() - t0).toFixed(0)}ms`);
```

⚠️ **Реальний вимір** (Node.js v24): `Stable: 48ms`, `Unstable: 47ms` — практично без різниці на цій машині й версії рушія. Це не спростовує саму ідею стабільності типів (вона задокументована командою V8 і використовується в багатьох реальних кейсах, особливо в гарячих циклах над великими типізованими масивами), але означає, що конкретна старіша цифра «5x» для цього найпростішого прикладу (`a + b`) на сучасному V8 більше не відтворюється — рушій навчився ефективніше обробляти цей випадок. Висновок той самий, що й у нотатці про hidden classes: перевіряйте на власному рушії й не переносьте застарілі числа як факт; принцип «одна функція — один стабільний тип» лишається доброю практикою для гарячого коду, навіть якщо на простих прикладах різниця сьогодні менш помітна, ніж раніше.

## Де це найбільш критично

1. Математичні функції — цикли з обчисленнями.
2. Обробка масивів — `map`, `filter`, `reduce` на великих даних.
3. Game loops — функції, що викликаються 60 разів на секунду.
4. Обробка даних від API — неявні типи (`string` замість `number`).

Для коду, що виконується рідко, нестабільність типів не має помітного впливу.

## Підсумок

| Стан функції | Відносна швидкість | Причина |
|---|---|---|
| Monomorphic (SMI) | найшвидше | прямий машинний код |
| Monomorphic (Double) | трохи повільніше | float-операції |
| Polymorphic (2–4 типи) | помітно повільніше | перевірка типу + кілька шляхів |
| Megamorphic (5+ типів) | значно повільніше | runtime lookup |
| Після деоптимізації | найповільніше | інтерпретація |

(Конкретні мілісекунди навмисно не наведені в таблиці — вони застарівають з кожною версією рушія, детально розділ 7.)

- V8 проходить три рівні компіляції (Ignition → Sparkplug → TurboFan), і TurboFan компілює код під конкретні спостережені типи.
- Навіть у межах «number» є SMI / HeapNumber (Double) / BigInt — з різною швидкістю обробки.
- Monomorphic (1 тип) → polymorphic (2–4 типи) → megamorphic (5+ типів) — кожен рівень у теорії повільніший за попередній, але сучасний V8 у простих випадках закриває значну частину цього розриву.
- Деоптимізація (guard не пройшов) відкидає оптимізований код і повертає функцію до повільнішого виконання.
- Тип масиву може тільки деградувати (SMI → Double → Mixed), назад — ніколи.
- TypeScript перевіряє типи лише на етапі компіляції й не захищає від нестабільності типів у рантаймі (зовнішні дані, `as any`).

Ключовий принцип: функція повинна завжди отримувати один і той самий тип даних. Якщо це неможливо — явно конвертуй тип на вході, щоб внутрішня логіка функції працювала з одним типом. Але перш ніж оптимізувати заради цього конкретний гарячий шлях, виміряйте реальний ефект на своєму рушії (розділ 7) — інтуїція з застарілих матеріалів може вводити в оману.
