# V8: конкатенація рядків та ropes

## Загальна ідея

Рядки в JS імутабельні (детально в `common/data-structures/String/String.js`) — кожна операція над рядком (конкатенація, `slice`, `replace`) створює новий рядок, а не змінює старий. У гарячому циклі це означає багато проміжних алокацій — саме тому наївна конкатенація в циклі є однією з найпоширеніших «прихованих» причин повільного коду.

Основне правило: не буди рядок через `+=` у циклі. Збирай шматки в масив і роби один `join()` у кінці, або (для V8) покладайся на ropes, розуміючи їхні обмеження.

## 1. Чому `+=` у циклі повільний (наївна модель)

Якби рядки завжди копіювались «буквально», кожен `+=` означав би: виділи пам'ять під новий рядок довжиною (стара довжина + нова частина) → скопіюй увесь старий вміст у нову пам'ять → допиши нову частину → стара пам'ять стає сміттям. На N ітерацій циклу з конкатенацією це давало б `O(N²)` складність копіювання (кожна ітерація копіює дедалі довший рядок).

```js
function buildHTMLNaive(items) {
  let html = "";
  for (const item of items) {
    html += `<li>${item}</li>`; // потенційно новий рядок щоразу
  }
  return html;
}
```

## 2. Що насправді робить V8: ropes (ConsString)

V8 не настільки наївний: для конкатенації довгих рядків він може створити внутрішню структуру ConsString («rope») — об'єкт, що просто зберігає посилання на ліву й праву частини, а не копіює вміст одразу:

```text
"abc" + "def" → ConsString { left: "abc", right: "def" }
(реальне копіювання відкладається до моменту, коли рядок потрібно
прочитати як один суцільний буфер — наприклад, indexOf(), charAt())
```

Це зм'якшує проблему для простого накопичення (`+=` у циклі), але:

- ConsString-дерево може стати глибоким при тисячах конкатенацій — кожна операція читання (не тільки фінальний вивід) змушує «сплющити» (flatten) усе дерево в суцільний буфер, і це `O(N)` операція, яка може відбутись у неочікуваний момент;
- якщо в циклі між конкатенаціями відбувається читання рядка (наприклад, `.length` перевіряється рідко — це ок, а от `.charAt()` чи regex-перевірка всередині циклу — вже ні), rope доводиться сплющувати раз у раз, і виграш зникає.

Висновок: покладатись на «може, V8 і так оптимізує» — ненадійно. Явний патерн з масивом і `join()` передбачуваний у будь-якому рушії.

## Правила

### Правило 1: збирай шматки в масив, роби один `join()` у кінці

```js
const itemsForHtml = ["Apple", "Banana", "Cherry"];

// ❌ Потенційно повільно на великих обсягах / зі "змішаним" читанням
function buildHTMLBad(items) {
  let html = "";
  for (const item of items) {
    html += `<li>${item}</li>`;
  }
  return html;
}

// ✅ Передбачувано швидко: одна фінальна конкатенація
function buildHTML(items) {
  const parts = new Array(items.length);
  for (let i = 0; i < items.length; i++) {
    parts[i] = `<li>${items[i]}</li>`;
  }
  return parts.join("");
}
console.log(buildHTML(itemsForHtml)); // <li>Apple</li><li>Banana</li><li>Cherry</li>
```

### Правило 2: уникай регулярних виразів і пошуку всередині циклу накопичення

```js
// ❌ Кожна ітерація змушує V8 "сплющити" rope, щоб виконати .includes()
function buildLogBad(events) {
  let log = "";
  for (const event of events) {
    if (!log.includes(event.type)) { // читання всередині циклу накопичення!
      log += `${event.type}: ${event.message}\n`;
    }
  }
  return log;
}
```

```js
// ✅ Розділи фази: спочатку збери дані (без читання проміжного рядка),
// потім один раз сформуй фінальний рядок
function buildLog(events) {
  const seen = new Set();
  const lines = [];
  for (const event of events) {
    if (!seen.has(event.type)) {
      seen.add(event.type);
      lines.push(`${event.type}: ${event.message}`);
    }
  }
  return lines.join("\n");
}
```

### Правило 3: для великих обсягів тексту — `Buffer`/потоки (Node.js)

Якщо йдеться про серйозну обробку тексту (генерація великих файлів, серіалізація) — рядки взагалі не найкращий інструмент. У Node.js для цього існують `Buffer`/потоки (streams), які пишуть байти напряму, без проміжних рядкових об'єктів:

```js
const chunks = [];
readableStream.on("data", (chunk) => chunks.push(chunk));
readableStream.on("end", () => {
  const full = Buffer.concat(chunks); // одна алокація, без rope-дерев
});
```

Детально — нотатка про `Buffer` (`node/core-concepts/buffers/buffer.md`) та потоки (`node/core-concepts/streams/`).

### Правило 4: template literals — не безкоштовні, але й не «особливо повільні»

Шаблонні рядки `` `${a}${b}` `` компілюються приблизно в той самий код, що й ручна конкатенація — вони не мають прихованого overhead понад звичайний `+`. Головне джерело повільності — сама частота конкатенацій у циклі, а не синтаксис:

```js
const a = "x";
const b = "y";
console.log(`${a}${b}` === a + b); // true — семантично те саме
```

## Вплив на продуктивність — чесний бенчмарк

```js
const { performance } = require("perf_hooks");
const N = 100000;
const bigItems = Array.from({ length: N }, (_, i) => `item-${i}`);

let t0 = performance.now();
let concatResult = "";
for (const item of bigItems) {
  concatResult += `<li>${item}</li>`;
}
console.log(`+= у циклі:        ${(performance.now() - t0).toFixed(0)}ms (length=${concatResult.length})`);

t0 = performance.now();
const partsResult = new Array(bigItems.length);
for (let i = 0; i < bigItems.length; i++) {
  partsResult[i] = `<li>${bigItems[i]}</li>`;
}
const joined = partsResult.join("");
console.log(`Array + join():    ${(performance.now() - t0).toFixed(0)}ms (length=${joined.length})`);
```

**Реальний вимір** (Node.js v24): `+= у циклі: 17мс`, `Array + join(): 7мс` — приблизно у 2.4 рази швидше для явного патерну з масивом, попри те що V8 тут якраз і застосовує rope-оптимізацію для `+=` (немає читання рядка всередині цього конкретного циклу, тож це «найкращий сценарій» для `+=`). Різниця стає значно помітнішою, коли між конкатенаціями є читання рядка (`indexOf`/`includes`/regex, розділ «правило 2») — саме тоді rope-модель V8 змушена постійно «сплющуватись», і `+=` деградує до `O(N²)`.

## Підсумок

- Рядки в JS імутабельні — кожна операція повертає новий рядок.
- V8 намагається «згладити» `+=` у циклі внутрішньою структурою ConsString (rope), але це не гарантія — читання рядка всередині циклу накопичення (`includes`/regex/`charAt`) змушує rope сплющуватись раз у раз і зводить оптимізацію нанівець.
- Надійний патерн: збирай частини в масив (pre-allocated, якщо розмір відомий — детально нотатка про оптимізацію алокацій) і роби один `join()` у кінці.
- Для великих обсягів байтових даних у Node.js — `Buffer`/потоки замість рядків узагалі.
- Template literals не мають прихованого overhead понад ручний `+`, проблема саме в частоті конкатенацій, а не в синтаксисі.
- Навіть коли `+=` у циклі показує прийнятний результат (як у вимірі вище, де rope працює у сприятливих умовах), явний масив + `join()` усе одно швидший і, головне, передбачуваний незалежно від того, чи трапиться десь поруч читання рядка, яке зламає rope-оптимізацію.

Ключовий принцип: не покладайся на те, що рушій «якось оптимізує» накопичення рядка — пиши код, який швидкий незалежно від внутрішньої реалізації рушія (масив + `join()`).
