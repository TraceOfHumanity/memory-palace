# WebAssembly: загальна характеристика

## Ключові відомості

| Параметр | Характеристика |
|---|---|
| Стандартизація | W3C (робоча група WebAssembly); специфікація 1.0 — W3C Recommendation, 2019 |
| Перша реалізація | 2017 (мінімально життєздатний продукт, MVP, у всіх основних браузерах) |
| Природа | переносимий низькорівневий бінарний формат інструкцій для віртуальної машини |
| Модель обчислень | стекова віртуальна машина |
| Типізація | статична; базові типи `i32`, `i64`, `f32`, `f64`, `v128` |
| Пам'ять | лінійна: суцільний масив байтів, зростає сторінками по 64 КіБ |
| Формати | `.wasm` (бінарний), `.wat` (текстовий, S-вирази) |
| Середовища виконання | браузери, Node.js, Deno, Wasmtime, Wasmer та інші |
| Безпека | ізольована пісочниця, валідація модуля перед виконанням |

## 1. Що таке WebAssembly

**WebAssembly** (скорочено **Wasm**) — це не мова асемблера в класичному розумінні, а **переносимий бінарний формат** низькорівневих інструкцій для віртуальної машини, вбудованої в браузер (та інші середовища). Формат подібний до асемблера за рівнем абстракції, але призначений не для конкретного процесора, а для **абстрактної машини**, яку рушій переводить у машинний код цільової архітектури (зокрема AArch64 на Apple Silicon, див. `arm64.md`).

Wasm не замінює [[javascript]], а **доповнює** його: JavaScript лишається мовою оркестрації, доступу до DOM і Web API, тоді як Wasm виконує обчислювально важкі ділянки й дає змогу запускати в браузері код, написаний іншими мовами.

## 2. Історичний контекст

Передумовою була проблема продуктивності: JavaScript, будучи динамічною мовою, важко оптимізувати для обчислень. Спершу з'явилися підходи через підмножину JS: **asm.js** (Mozilla, 2013) — суворо типізована підмножина JavaScript, яку рушій міг компілювати особливо ефективно, та **Emscripten**, компілятор C/C++ у asm.js. Наступним кроком стало **WebAssembly**: компактний бінарний формат, що швидше завантажується й розбирається. Розробку спільно вели Mozilla, Google, Microsoft та Apple; станом на 2017 рік MVP підтримували всі основні браузери, а 2019 року специфікацію 1.0 затверджено як рекомендацію W3C.

Пізніші розширення (зокрема SIMD, масові операції з пам'яттю, референсні типи, обробка винятків, збирач сміття) розвивають платформу як універсальне середовище виконання, включно з не-браузерними сценаріями через інтерфейс **WASI**.

## 3. Принципи дизайну

1. **Переносимість.** Один `.wasm`-файл виконується на будь-якій архітектурі й ОС, де є середовище виконання.
2. **Швидкість, близька до нативної.** Формат розроблено так, щоб швидко транслюватися в машинний код (AOT або JIT).
3. **Безпека.** Модуль працює в пісочниці: не має прямого доступу до системи; усе зовнішнє (файли, мережа, DOM) отримує лише через явно **імпортовані** функції.
4. **Детермінованість і валідація.** Модуль перевіряється перед виконанням; його поведінка чітко визначена (з невеликою кількістю винятків).
5. **Компактність.** Бінарне кодування економить трафік і прискорює розбір.
6. **Відкритість.** Є текстовий формат для читання й налагодження.

## 4. Модель виконання

Wasm-код організовано в **модулі**. Модуль містить: типи функцій, функції, лінійну пам'ять, таблиці (посилання на функції), глобальні змінні, **імпорти** та **експорти**. Вирази обчислюються на **стеку значень**: інструкція бере операнди зі стека й кладе результат назад.

Приклад функції додавання у текстовому форматі (WAT):

```wat
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0        ;; кладемо перший параметр на стек
    local.get 1        ;; кладемо другий параметр
    i32.add))          ;; беремо два значення, кладемо суму
```

Керування виконанням — **структуроване**: є блоки `block`, `loop`, `if` та переходи `br`, але довільного `goto` немає. Це дає змогу швидко перевіряти коректність модуля й унеможливлює перехід у довільне місце коду.

## 5. Взаємодія з JavaScript

JavaScript завантажує й запускає Wasm через глобальний об'єкт `WebAssembly`. Нижче — той самий модуль у вигляді байтів (без зовнішніх інструментів), що працює у Node.js і в браузері:

```js
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00,       // сигнатура "\0asm" і версія 1
  0x01, 0x07, 0x01, 0x60, 0x02, 0x7f, 0x7f, 0x01, 0x7f, // секція типів: (i32, i32) -> i32
  0x03, 0x02, 0x01, 0x00,                               // секція функцій
  0x07, 0x07, 0x01, 0x03, 0x61, 0x64, 0x64, 0x00, 0x00, // експорт "add"
  0x0a, 0x09, 0x01, 0x07, 0x00,                         // секція коду
  0x20, 0x00, 0x20, 0x01, 0x6a, 0x0b,                   // local.get 0, local.get 1, i32.add, end
]);

const { instance } = await WebAssembly.instantiate(bytes);
console.log(instance.exports.add(40, 2)); // 42
```

Основні складники JS API:

- `WebAssembly.instantiate` / `instantiateStreaming` — компіляція та створення екземпляра (потокове завантаження з `fetch` є найефективнішим у браузері);
- `WebAssembly.Module`, `WebAssembly.Instance` — скомпільований модуль та його екземпляр;
- `WebAssembly.Memory` — лінійна пам'ять, доступна з JS як `ArrayBuffer` (для обміну даними використовують типізовані масиви, `Uint8Array` тощо);
- імпорти — об'єкт із JS-функціями, які модуль може викликати.

Особливості обміну значеннями: числа `i32`, `f32`, `f64` відображаються на JS-число, `i64` — на `BigInt`. Складні дані (рядки, масиви, структури) **передаються через лінійну пам'ять**: JS записує байти в пам'ять модуля й передає в функцію зсув (адресу) та довжину. Автоматизують це інструменти на кшталт `wasm-bindgen` (Rust) та Emscripten.

## 6. Джерела Wasm-модулів

Модуль зазвичай не пишуть вручну, а отримують компіляцією:

- **C / C++** — Emscripten або `clang --target=wasm32`;
- **Rust** — ціль `wasm32-unknown-unknown`, `wasm-bindgen`, `wasm-pack`;
- **AssemblyScript** — мова з синтаксисом TypeScript, що компілюється у Wasm;
- **Go, Kotlin, C#** та інші — власні або експериментальні цілі;
- **вручну** — у форматі WAT (інструменти: WABT, `wasm-tools`) для навчання чи вузьких оптимізацій.

## 7. Сфери застосування

- **обчислювально важкі завдання в браузері:** обробка зображень і відео, кодеки, криптографія, фізика й 3D, CAD, аудіоедитори;
- **перенесення наявних бібліотек** у веб (SQLite, FFmpeg, OpenCV);
- **ігри** та застосунки з високим навантаженням на процесор;
- **серверні та периферійні (edge) сценарії:** плагіни в пісочниці, безсерверні функції, швидкий холодний старт;
- **безпечні плагіни** та розширюваність застосунків.

Wasm **не призначений** для роботи з DOM або для заміни JavaScript у звичайних застосунках: звернення до DOM іде через JS, а витрати на виклики між JS і Wasm нівелюють виграш у простих задачах.

## 8. Сильні сторони та обмеження

| Сильні сторони | Обмеження |
|---|---|
| Швидкість, близька до нативної | Немає прямого доступу до DOM і Web API |
| Переносимість між платформами | Складний обмін рядками та структурами даних |
| Безпечна пісочниця | Налагодження складніше, ніж у JS |
| Можливість використати код на C/C++/Rust | Розмір модулів і runtime може бути значним |
| Компактний формат, швидкий розбір | Потрібні інструменти збирання |

## 9. Поширені хибні уявлення

1. «WebAssembly — це асемблер для браузера». Це віртуальний формат, а не мова конкретного процесора.
2. «Wasm замінить JavaScript». Вони розраховані на співпрацю: Wasm — для обчислень, JS — для інтеграції з вебом.
3. «Wasm завжди швидший за JS». Для невеликих або DOM-орієнтованих задач виграшу може не бути, а сучасні JS-рушії дуже швидкі.
4. «Wasm працює тільки в браузері». Ні: він виконується в Node.js, Deno, окремих рантаймах (Wasmtime) та вбудовується в застосунки.
5. «Wasm небезпечний, бо це майже нативний код». Навпаки: модуль ізольований і має лише ті можливості, які надано через імпорти.
