# Big O нотація — як описувати швидкість росту алгоритму

Усі числа з прикладами нижче отримані реальним запуском (Node 24, V8). Підрахунок кроків точний; час у мілісекундах залежить від машини і наведений для порівняння порядків, а не як еталон.

## 1. Навіщо це потрібно

- Один і той самий код на швидкому комп'ютері працює 1 с, на повільному — 3 с. Секунди не описують **алгоритм**, вони описують **машину**.
- Нас цікавить інше: **як зростає кількість роботи, коли зростає вхід `n`**. Подвоїли дані — час подвоївся? збільшився в 4 рази? майже не змінився?
- Big O дає мову для відповіді: `O(1)`, `O(log n)`, `O(n)`, `O(n log n)`, `O(n²)`, `O(2ⁿ)`, `O(n!)`.
- Big O відповідає на питання «що буде, коли даних стане у 1000 разів більше», а не «скільки мілісекунд це займе сьогодні».

## 2. Що саме ми рахуємо

Не секунди, а **кількість елементарних операцій** як функцію розміру входу `n`: порівняння, присвоєння, звернення до елемента, арифметика. Кожну вважаємо `1` крок.

- `n` — розмір входу: довжина масиву, кількість символів у рядку, кількість вузлів у дереві, кількість користувачів.
- Якщо входів кілька (два масиви довжин `a` і `b`), то складність залежить від обох: `O(a + b)` або `O(a · b)`.
- Для числа `n` як **значення** (наприклад, `isPrime(n)`) розмір входу — кількість його цифр, а не само число; у «школярських» оцінках зазвичай рахують відносно значення `n`.

## 3. Формальне означення

`f(n) = O(g(n))` означає: існують сталі `c > 0` і `n₀` такі, що для всіх `n ≥ n₀` виконується `f(n) ≤ c · g(n)`.

Словами: починаючи з якогось розміру, `f` не росте швидше за `g` з точністю до сталого множника. Big O — це **верхня межа**.

Приклад: `f(n) = 3n + 5`. Беремо `c = 4`, `n₀ = 5`: для `n ≥ 5` маємо `3n + 5 ≤ 4n`. Отже `3n + 5 = O(n)`.
Реальні значення при `n = 1 000 000`: `3n + 5 = 3 000 005`, а `n = 1 000 000` — той самий порядок, різниця лише у множнику 3.

Спрощення, які випливають з означення:
1. **Відкидаємо сталі множники:** `O(3n)` = `O(n)`, `O(n/2)` = `O(n)`.
2. **Відкидаємо молодші доданки:** `n² + n` = `O(n²)`. При `n = 1000`: `1 001 000` проти `1 000 000`; при `n = 10⁶`: `1 000 001 000 000` проти `10¹²`.
3. **Основа логарифма неважлива:** `log₂ n` і `log₁₀ n` відрізняються сталим множником, тому пишуть просто `O(log n)`.
4. `O(n)` формально також `O(n²)` (верхня межа не мусить бути точною), але на практиці завжди пишуть **найщільнішу** межу.

## 4. Правила підрахунку складності коду

| Конструкція | Складність |
|---|---|
| Окремий оператор (арифметика, присвоєння, доступ `a[i]`) | `O(1)` |
| Цикл до `n` | `O(n)` |
| Два цикли **один за одним** | `O(n + n)` = `O(n)` — додаємо |
| Цикл у циклі | `O(n · n)` = `O(n²)` — множимо |
| Цикл, де змінна множиться/ділиться (`i *= 2`, `i = floor(i/2)`) | `O(log n)` |
| Внутрішній цикл від `i + 1` до `n` | `n(n−1)/2` кроків = `O(n²)` |
| Цикл `while (i * i <= n)` | `O(√n)` |
| `if` / `else` | береться **гірша** гілка |
| Виклик функції | складність цієї функції |
| Різні входи `a` і `b` | `O(a + b)` або `O(a · b)`, а не `O(n)` |

Виміряні підрахунки кроків:
- два цикли по `n = 1000` один за одним → `2000` кроків (= `O(n)`);
- вкладені цикли `n = 1000` → `1 000 000` кроків (`n²`);
- `for i<n, for j=i+1..n` → `499 500` кроків = `n(n−1)/2`;
- `for (i = 1; i <= 1e6; i *= 2)` → `20` кроків (= `log₂ 10⁶ ≈ 19.9`);
- `i = 10⁶; i >= 1; i = floor(i/2)` → `20` кроків;
- `for (i = 1; i*i <= 10⁶; i++)` → `1000` кроків (= `√10⁶`);
- `for i<1000, for (j = 1; j < 1000; j *= 2)` → `10 000` кроків = `n · log n`.

## 5. Класи складності — від найшвидшого до найповільнішого

### O(1) — константа
Кількість кроків не залежить від `n`: `arr[i]`, `map.get(k)`, `obj.key`, `stack.push` (амортизовано), перевірка парності, `arr.length`.
```js
const first = arr[0];            // 1 крок для масиву з 10 і з 10 000 000 елементів
```

### O(log n) — логарифм
Щоразу відкидаємо половину даних. Бінарний пошук у відсортованому масиві. Виміряно (найгірший випадок, елемента немає):

| n | лінійний пошук | бінарний пошук |
|---|---|---|
| 10 | 10 | 3 |
| 100 | 100 | 6 |
| 1 000 | 1 000 | 9 |
| 1 000 000 | 1 000 000 | 19 |

Мільйон елементів — це лише ~20 кроків. Подвоїв дані — додався **один** крок.
```js
function binarySearch(a, x) {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (a[mid] === x) return mid;
    a[mid] < x ? (lo = mid + 1) : (hi = mid - 1);
  }
  return -1;
}
```
Вимога: масив **відсортований**. Інші приклади: пошук у збалансованому BST, висота купи, піднесення до степеня подвоєнням.

### O(√n)
Перебір дільників до кореня: `for (i = 2; i * i <= n; i++)`. Для `n = 10⁶` це 1000 кроків.

### O(n) — лінійна
Один прохід: сума, максимум, `includes`, `indexOf`, `filter`, `map`, `forEach`, `reduce`, копіювання масиву (`slice`, `[...a]`), `join`. Виміряно: лінійний пошук у масиві з 10⁶ елементів — від 1 кроку (елемент перший) до `1 000 000` (останній або відсутній); у середньому ~`500 001`.

### O(n log n) — лінійно-логарифмічна
Ефективні сортування: merge sort, heap sort, quick sort (у середньому), вбудований `Array.prototype.sort` (TimSort). Виміряно кількість порівнянь merge sort на випадкових даних:

| n | порівнянь | n · log₂ n |
|---|---|---|
| 10 | 25 | 33 |
| 100 | 535 | 664 |
| 1 000 | 8 713 | 9 966 |
| 10 000 | 120 472 | 132 877 |

Нижня межа для сортування порівняннями — `Ω(n log n)`: швидше не вийде.

### O(n²) — квадратична
Вкладені цикли по тих самих даних: bubble/selection/insertion sort, перевірка всіх пар. Виміряно: bubble sort на зворотному масиві: `n = 10` → `45` порівнянь, `n = 100` → `4950`, `n = 1000` → `499 500`. Збільшили `n` у 10 разів — роботи в ~100 разів більше.

### O(n³)
Три вкладені цикли: множення матриць «в лоб».

### O(2ⁿ) — експонента
Наївний рекурсивний Фібоначчі. Виміряно кількість викликів `fib(n)`:

| n | результат | викликів |
|---|---|---|
| 5 | 5 | 15 |
| 10 | 55 | 177 |
| 20 | 6 765 | 21 891 |
| 30 | 832 040 | 2 692 537 |

Час: `fib(30)` ≈ 8 мс, `fib(35)` ≈ 92 мс (в ~11 разів довше за +5 кроків; приблизно ×1.6 за кожну одиницю `n`). Усі підмножини множини з `n` елементів: `2ⁿ` (n = 20 → `1 048 576`).
З мемоізацією той самий `fib(30)` — лише **59** викликів, `O(n)`.

### O(n!) — факторіал
Усі перестановки: `n = 3..8` → `6, 24, 120, 720, 5040, 40320`. `20! = 2 432 902 008 176 640 000`, `25! = 15 511 210 043 330 985 984 000 000`. Задача комівояжера перебором.

## 6. Порівняння зростання (виміряні/пораховані значення)

| n | log₂ n | n log₂ n | n² | n³ | 2ⁿ | n! |
|---|---|---|---|---|---|---|
| 10 | 3.3 | 33 | 100 | 1 000 | 1 024 | 3 628 800 |
| 100 | 6.6 | 664 | 10 000 | 10⁶ | ≈10³⁰ | ≈10¹⁵⁸ |
| 1 000 | 10 | 9 966 | 10⁶ | 10⁹ | ≈10³⁰¹ | — |
| 10 000 | 13.3 | 132 877 | 10⁸ | 10¹² | — | — |
| 100 000 | 16.6 | 1 660 964 | 10¹⁰ | 10¹⁵ | — | — |
| 1 000 000 | 19.9 | 19 931 569 | 10¹² | 10¹⁸ | — | — |

Для орієнтира: `2¹⁰ = 1024`, `2²⁰ = 1 048 576`, `2³⁰ = 1 073 741 824`, `2⁵⁰ = 1 125 899 906 842 624`.

Порядок: `O(1) < O(log n) < O(√n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)`.

## 7. Практичний орієнтир: скільки операцій реально встигаєш

Грубо, JS виконує ~10⁷–10⁸ простих операцій за секунду. Тому за розміром входу можна оцінити, яка складність прийнятна за ~1 с:

| n до | прийнятна складність |
|---|---|
| ~10 | `O(n!)` |
| ~20–25 | `O(2ⁿ)` |
| ~500 | `O(n³)` |
| ~5 000–10 000 | `O(n²)` |
| ~10⁶ | `O(n log n)` |
| ~10⁷–10⁸ | `O(n)` |
| практично необмежено | `O(log n)`, `O(1)` |

Виміряно: перевірка дублікатів «кожен з кожним» при `n = 10 000` → 19 мс, `20 000` → 72 мс, `40 000` → 286 мс (час зростає в ~4 рази при подвоєнні `n` — це і є `n²`). Версія через `Set` для `n = 10⁶` — 52 мс.

## 8. Найкращий, найгірший і середній випадок

Один алгоритм може мати різну складність залежно від даних:

| Алгоритм | Найкращий | Середній | Найгірший |
|---|---|---|---|
| Лінійний пошук | `O(1)` (елемент перший) | `O(n)` (~n/2) | `O(n)` |
| Бінарний пошук | `O(1)` (посередині) | `O(log n)` | `O(log n)` |
| Bubble sort без прапорця | `O(n²)` | `O(n²)` | `O(n²)` |
| Bubble sort з ранньою зупинкою | `O(n)` (вже відсортований: `999` порівнянь для n = 1000) | `O(n²)` | `O(n²)` |
| Insertion sort | `O(n)` | `O(n²)` | `O(n²)` |
| Merge sort | `O(n log n)` | `O(n log n)` | `O(n log n)` |
| Quick sort | `O(n log n)` | `O(n log n)` | `O(n²)` (погано обраний опорний елемент) |
| Hash table get | `O(1)` | `O(1)` | `O(n)` (усі ключі в одному кошику) |

Якщо кажуть просто «Big O алгоритму» — зазвичай мають на увазі **найгірший** випадок (гарантія зверху).

## 9. Big O, Ω, Θ (і малі o, ω)

- `O(g)` — верхня межа («не гірше ніж»).
- `Ω(g)` (Омега) — нижня межа («не краще ніж»). Сортування порівнянням — `Ω(n log n)`.
- `Θ(g)` (Тета) — точна межа: і `O(g)`, і `Ω(g)`. Merge sort — `Θ(n log n)` у всіх випадках.
- `o(g)`, `ω(g)` — строгі версії (росте строго повільніше / швидше).
- У повсякденній розмові «O» вживають і там, де коректніше «Θ»; на співбесідах це зазвичай нормально.

## 10. Складність за пам'яттю (space complexity)

Скільки **додаткової** пам'яті потрібно залежно від `n` (вхід зазвичай не рахують — це «auxiliary space»).

| Код | Пам'ять |
|---|---|
| Кілька змінних | `O(1)` |
| Новий масив/Set/Map розміру `n` | `O(n)` |
| Матриця `n × n` | `O(n²)` |
| Рекурсія глибиною `d` | `O(d)` — стек викликів |
| Рекурсивний merge sort | `O(n)` (допоміжні масиви) |
| Бінарний пошук ітеративно / рекурсивно | `O(1)` / `O(log n)` |

Приклад: рекурсія `d(n) = n === 0 ? 0 : 1 + d(n - 1)` — глибина `n` → `O(n)` пам'яті. Виміряно: глибина `10 000` проходить, глибина `20 000` дає `RangeError: Maximum call stack size exceeded` (ліміт залежить від рушія й розміру кадру).

Типовий компроміс «час ↔ пам'ять»: пошук дубліката — `O(n²)` часу і `O(1)` пам'яті **або** `O(n)` часу і `O(n)` пам'яті (через `Set`).

## 11. Амортизована складність

Окрема операція інколи дорога, але в середньому по серії — дешева.

- `array.push(x)`: зазвичай `O(1)`, але коли внутрішній буфер заповнений, рушій виділяє більший і копіює — `O(n)`. Оскільки буфер росте кратно (в ~1.5–2 рази), на `n` вставок припадає загалом `O(n)` роботи → **амортизовано `O(1)`**. Виміряно: 10⁶ `push` ≈ 5 мс.
- Динамічний масив, хеш-таблиця (rehash), стек/черга на масивах — тож те саме.
- Амортизована ≠ середня: «середня» — по всіх можливих входах, «амортизована» — по послідовності операцій у найгіршому випадку.

## 12. Рекурсія і рекурентні співвідношення

Для рекурсії складають рівняння `T(n)`:
- Лінійна рекурсія `f(n) = f(n−1) + O(1)` → `T(n) = n` → `O(n)`.
- Бінарний пошук: `T(n) = T(n/2) + O(1)` → `O(log n)`.
- Merge sort: `T(n) = 2·T(n/2) + O(n)` → `O(n log n)`.
- Наївний Фібоначчі: `T(n) = T(n−1) + T(n−2) + O(1)` → `≈ O(φⁿ)`, спрощено `O(2ⁿ)` (φ ≈ 1.618; видно у виміряних викликах — зростання ~×1.6 за крок).

**Майстер-теорема** (Master theorem) для `T(n) = a·T(n/b) + O(nᵈ)`:
- якщо `d > log_b a` → `O(nᵈ)`;
- якщо `d = log_b a` → `O(nᵈ · log n)`;
- якщо `d < log_b a` → `O(n^(log_b a))`.
Merge sort: `a = 2, b = 2, d = 1` → `d = log₂2 = 1` → `O(n log n)`. Бінарний пошук: `a = 1, b = 2, d = 0` → `d = log₂1 = 0` → `O(log n)`.

Мемоізація/динамічне програмування збиває експоненту до полінома: `fib` з `Map` — 59 викликів для `n = 30` замість 2 692 537.

Виміряні ілюстрації:

- `shift` у циклі до порожнього масиву: `n = 20 000` → 25 мс, `40 000` → 120 мс, `80 000` → 500 мс (×4 на подвоєння = квадрат). `pop` у циклі: стабільно ≈0.1 мс. (На маленьких масивах V8 має оптимізацію — для `n = 10 000` лише ~1 мс; не покладайся на неї.)
- Накопичення `r = [...r, x]` у циклі: `n = 5 000` → 18 мс, `10 000` → 43 мс, `20 000` → 435 мс, `40 000` → 2149 мс — це `O(n²)`, хоча виглядає як один цикл.
- `sort` числових масивів: `n = 100 000` → 25 мс, `200 000` → 66 мс, `400 000` → 143 мс, `800 000` → 289 мс — трохи більше ніж ×2 на подвоєння = `n log n`.
- Two-sum на 20 000 елементів: вкладені цикли ≈223 мс, через `Map` ≈1.7 мс.

## 14. Типові способи прискорення (патерни)

1. **Хеш-таблиця (`Set`/`Map`/об'єкт)** замість внутрішнього циклу пошуку: `O(n²)` → `O(n)` (two-sum, дублікати, частоти).
2. **Сортування + два вказівники**: `O(n²)` → `O(n log n)`.
3. **Бінарний пошук** замість лінійного на відсортованих даних: `O(n)` → `O(log n)`.
4. **Мемоізація / DP**: `O(2ⁿ)` → `O(n)`.
5. **Префіксні суми**: запит суми на відрізку `O(n)` → `O(1)` після `O(n)` підготовки.
6. **Ковзне вікно**: `O(n·k)` → `O(n)`.
7. **Купа (heap)** для top-k: `O(n log k)` замість повного сортування.
8. **Черга замість `shift()`**: індекс «голови» або зв'язний список — `O(1)` замість `O(n)`.
9. **Збирати частини в масив і `join`** замість повторного створення масивів/рядків у циклі.

## 15. Типові помилки

1. **Рахувати сталі:** `O(2n)` або `O(n + 5)` — завжди `O(n)`.
2. **Складати замість множити (і навпаки):** два цикли поспіль → `+`, вкладені → `×`.
3. **Забути про приховані цикли:** `includes`, `indexOf`, `slice`, `shift`, `splice`, spread `[...a]` усередині циклу роблять `O(n²)`.
4. **Один `n` для різних входів:** обхід двох масивів довжин `a` і `b` — `O(a + b)`, а не `O(n)`.
5. **Плутати найгірший і середній випадок** (quick sort, хеш-таблиця).
6. **Вважати `O(1)` «швидко»:** `O(1)` з великою сталою може бути повільніше за `O(n)` на малих `n`. Big O описує зростання, не абсолютну швидкість.
7. **Ігнорувати пам'ять:** швидкий алгоритм з `O(n²)` пам'яттю для `n = 10⁵` не влізе.
8. **Мікрооптимізація замість Big O:** замінити `O(n²)` на `O(n log n)` дасть набагато більше, ніж «швидший» цикл.
9. **Рекурсія без урахування стеку:** `O(n)` глибина → `RangeError` на великих `n`.
10. **Вважати, що `Set.has` завжди `O(1)`:** у гіршому випадку (колізії) повільніше; практично — `O(1)`.
11. **Забути, що вхід — число:** складність `isPrime(n)` ділениням `O(√n)` — експоненційна відносно **кількості цифр** `n`.
12. **Не вимірювати:** Big O — модель; на реальних даних перевіряй `performance.now()`/профайлером.

## 16. Як оцінювати складність: покроковий алгоритм

1. Визнач, що є `n` (або кілька входів).
2. Знайди цикли, рекурсію і виклики вбудованих методів.
3. Для кожного рядка запиши складність (враховуй приховані цикли в методах).
4. Послідовні блоки — **додай**, вкладені — **перемнож**.
5. Для рекурсії запиши `T(n)` і розв'яжи (дерево викликів або Master theorem).
6. Залиш лише **найстарший доданок**, викинь сталі.
7. Окремо оціни **пам'ять** (включно зі стеком рекурсії).
8. Перевір найгірший, середній і найкращий випадок.
9. За таблицею розділу 7 визнач, чи вистачить при очікуваному `n`.

## 17. Приклад повного розбору

```js
function hasDuplicate(a) {          // n = a.length
  for (let i = 0; i < a.length; i++)          // n разів
    for (let j = i + 1; j < a.length; j++)    // у середньому n/2 разів
      if (a[i] === a[j]) return true;         // O(1)
  return false;
}
// кроків: n(n−1)/2 → O(n²) часу, O(1) пам'яті

function hasDuplicateFast(a) {
  const seen = new Set();                     // O(n) пам'яті
  for (const x of a) {                        // n разів
    if (seen.has(x)) return true;             // O(1)
    seen.add(x);                              // O(1)
  }
  return false;
}
// O(n) часу, O(n) пам'яті
```
Виміряно: `n = 40 000` → ≈286 мс проти `Set`-версії для `n = 10⁶` → ≈52 мс.

## 18. Підсумок
- Big O — це **швидкість зростання** кількості операцій при зростанні входу, верхня межа.
- Відкидаємо сталі й молодші доданки; рахуємо найгірший випадок.
- Класи: `1 < log n < √n < n < n log n < n² < n³ < 2ⁿ < n!`.
- Послідовне — додаємо, вкладене — множимо, ділення навпіл — `log n`.
- Окремо рахуємо час і пам'ять; рекурсія коштує стеком.
- Типове прискорення: хеш-таблиця, сортування, бінарний пошук, мемоізація.
- Орієнтир: ~10⁷–10⁸ операцій на секунду; `O(n²)` ще працює до ~10⁴, `O(n log n)` — до ~10⁶.
