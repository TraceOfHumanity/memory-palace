# SQLite: загальна характеристика

## Ключові відомості

| Параметр | Характеристика |
|---|---|
| Тип | вбудована реляційна база даних (бібліотека), без окремого сервера |
| Модель даних | реляційна, таблиці; динамічна типізація значень |
| Мова запитів | SQL |
| Автор | Д. Річард Гіпп (D. Richard Hipp) |
| Перший випуск | 2000 |
| Ліцензія | суспільне надбання (public domain) |
| Мова реалізації | C |
| Сховище | один звичайний файл на диску (або пам'ять) |
| Клієнт командного рядка | `sqlite3` |
| Розширення файлів | `.db`, `.sqlite`, `.sqlite3` |

## 1. Історичний контекст

SQLite створив 2000 року Д. Річард Гіпп під час роботи над програмним забезпеченням для військових кораблів: потрібна була база даних, яка не вимагає окремого сервера й адміністратора. Ця вимога визначила всю філософію проєкту. Автор публічно передав код у суспільне надбання, а розробку ведуть невелика команда та спільнота, зберігаючи виняткову стабільність формату файлів і зворотну сумісність.

Проєкт стверджує, що це, імовірно, найпоширеніша СКБД у світі: вона вбудована в операційні системи мобільних пристроїв (Android, iOS), браузери, застосунки для настільних комп'ютерів і безліч пристроїв.

## 2. Ключова ідея: без сервера

Більшість СКБД (див. [[postgresql]], [[mongodb]]) працюють як **окремий процес-сервер**, з яким застосунок спілкується мережею. SQLite — це **бібліотека**, що підключається до застосунку й читає та записує файл бази безпосередньо в його процесі. Наслідки:

- **нульова конфігурація**: немає установлення, користувачів, портів;
- уся база — **один файл**, який просто копіюється, пересилається чи архівується;
- відсутність мережевих витрат: виклик функції замість запиту через сокет;
- безпекою й доступом керує файлова система, а не сервер.

## 3. Модель даних і динамічна типізація

Дані зберігаються в таблицях, як у будь-якій реляційній базі. Але типізація в SQLite **динамічна**: тип належить значенню, а тип стовпця є лише «спорідненістю» (*type affinity*), тобто рекомендацією. Тому в стовпець, оголошений як `INTEGER`, за замовчуванням можна записати текст:

```sql
CREATE TABLE t (n INTEGER);
INSERT INTO t VALUES ('abc');       -- виконується без помилки
SELECT n, typeof(n) FROM t;         -- abc | text
```

Щоб отримати суворий контроль типів, створюють таблицю з ключовим словом `STRICT` (з версії 3.37). Класи зберігання: `NULL`, `INTEGER`, `REAL`, `TEXT`, `BLOB`. Окремого типу дати немає: час зберігають як текст, число (Unix-час) або дробове число (юліанський день).

## 4. Основні запити

```sql
CREATE TABLE notes (
    id    INTEGER PRIMARY KEY,      -- псевдонім для внутрішнього rowid
    title TEXT NOT NULL
);

INSERT INTO notes (title) VALUES ('Перша нотатка');

SELECT id, title FROM notes;
```

SQLite підтримує більшість стандартного SQL: `JOIN`, підзапити, загальні табличні вирази, віконні функції, індекси, тригери, представлення, повнотекстовий пошук (модуль FTS5), а також JSON-функції.

## 5. Транзакції та узгодженість

Усі зміни виконуються в **ACID-транзакціях**: навіть при збої живлення база лишається цілою. Це забезпечують журнал відкату (rollback journal) або режим **WAL** (write-ahead log), що вмикається командою `PRAGMA journal_mode = WAL;`.

Головне обмеження — **єдиний письменник**: у кожний момент запис може виконувати лише одне з'єднання (блокування на рівні всієї бази). Читачів може бути багато, а в режимі WAL читання не блокується записом. Тому SQLite чудово підходить для навантажень із перевагою читання, але не для великої кількості одночасних записів.

## 6. Особливості та пастки

- **Зовнішні ключі за замовчуванням вимкнено.** Їх потрібно вмикати для кожного з'єднання: `PRAGMA foreign_keys = ON;`.
- **Динамічна типізація** (розділ 3) вимагає дисципліни або `STRICT`.
- Обмежена підтримка змін схеми: деякі операції `ALTER TABLE` виконуються через створення нової таблиці.
- Мережевий доступ до файлу з кількох машин (наприклад, через NFS) не рекомендовано через проблеми блокувань.
- Максимальний розмір бази досягає сотень терабайтів, але практично визначається диском і схемою запитів.

## 7. Використання з JavaScript та WebAssembly

- **Node.js** має вбудований модуль `node:sqlite` (поки що позначений експериментальним), а також популярний пакет `better-sqlite3`.
- **Браузер:** SQLite скомпільовано в **WebAssembly** (офіційна збірка `sqlite-wasm`), тож базу можна запускати безпосередньо у вкладці, зберігаючи дані в Origin Private File System. Про формат Wasm докладніше — у нотатці `programming/assembly/webassembly/webassembly.md`.

## 8. Сфери застосування

- мобільні й настільні застосунки (локальне сховище);
- браузери та їхні внутрішні бази (історія, налаштування);
- формат обміну даними та конфігурація застосунків;
- локальна розробка, тестування, прототипи;
- невеликі та середні вебсайти з переважним читанням; edge-сценарії.

## 9. Сильні сторони та обмеження

| Сильні сторони | Обмеження |
|---|---|
| Нуль конфігурації, один файл | Один письменник одночасно |
| Дуже висока надійність та стабільність формату | Немає керування користувачами й доступом |
| Швидкість завдяки відсутності мережі | Слабкий підхід до горизонтального масштабування |
| Публічне надбання, невеликий розмір | Динамічна типізація потребує дисципліни |

## 10. Поширені хибні уявлення

1. «SQLite — іграшкова база для тестів». Вона застосовується в промисловому масштабі: мільярди пристроїв.
2. «SQLite не підтримує транзакцій». Підтримує повністю, з ACID.
3. «SQLite не може працювати паралельно». Читачів багато, обмеження лише на одночасний запис.
4. «Тип стовпця в SQLite суворий». Без `STRICT` він лише рекомендація.
