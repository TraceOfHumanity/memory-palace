# MongoDB: загальна характеристика

## Ключові відомості

| Параметр | Характеристика |
|---|---|
| Тип | документо-орієнтована NoSQL-база даних |
| Модель даних | документи у форматі BSON, згруповані в колекції |
| Мова запитів | MQL (MongoDB Query Language), конвеєр агрегації |
| Розробник | MongoDB, Inc. (до 2013 року — 10gen) |
| Перший випуск | 2009 |
| Ліцензія | SSPL (Server Side Public License) |
| Механізм зберігання | WiredTiger (з версії 3.2) |
| Порт за замовчуванням | 27017 |
| Клієнт командного рядка | `mongosh` |
| Хмарний сервіс | MongoDB Atlas |

## 1. Історичний контекст

MongoDB розроблено компанією 10gen, заснованою 2007 року Двайтом Мерріменом, Еліотом Горовицем і Кевіном Раяном; перший випуск СКБД відбувся 2009 року. Назва походить від англійського *humongous* («велетенський»). Компанію перейменовано на MongoDB, Inc. 2013 року. Поява системи пов'язана з рухом **NoSQL**, що виник як відповідь на потребу в горизонтальному масштабуванні та гнучкій схемі для вебзастосунків. 2018 року ліцензію змінено з AGPL на SSPL, яку Open Source Initiative не визнає відкритою; це варто враховувати при виборі.

## 2. Модель даних

Основна одиниця — **документ**: впорядкований набір пар «ключ-значення», що зберігається у форматі **BSON** (бінарний JSON). BSON додає до JSON типи, яких у ньому немає: `ObjectId`, `Date`, `Decimal128`, `Int32`, `Int64`, бінарні дані. Документи групуються в **колекції** (аналог таблиць), а колекції — у бази даних.

Кожен документ має унікальне поле `_id`; якщо його не задано, генерується `ObjectId` (12 байтів). Максимальний розмір документа — 16 МіБ. Документи можуть бути **вкладеними** й містити масиви, тому пов'язані дані часто зберігають разом в одному документі.

```js
db.users.insertOne({ email: "a@example.com", plan: "pro", tags: ["admin", "beta"] })

db.users.find({ plan: "pro" })

db.users.aggregate([
  { $group: { _id: "$plan", total: { $sum: 1 } } }
])
```

## 3. Проєктування даних: вбудовування чи посилання

Ключове рішення в MongoDB — як подавати зв'язки:

- **Вбудовування (embedding).** Пов'язані дані лежать у тому самому документі (наприклад, адреси користувача). Читання швидке (один запит), оновлення документа атомарне; але документ росте, а дані можуть дублюватися.
- **Посилання (referencing).** Документи посилаються один на одного через ідентифікатори (як зовнішні ключі); потрібен додатковий запит або операція `$lookup` (аналог `JOIN`).

Правило: вбудовуйте те, що читається разом і має обмежений розмір; посилайтеся на дані, що використовуються окремо або необмежено ростуть.

## 4. Схема

Схема **гнучка**: документи в одній колекції можуть мати різні поля. Це прискорює розробку, але відповідальність за узгодженість переходить до застосунку. Гнучкість не означає відсутність структури: MongoDB підтримує **валідацію схеми** (`$jsonSchema`), що змушує документи відповідати заданим правилам, а бібліотеки на кшталт Mongoose додають схеми на рівні застосунку.

## 5. Запити та індекси

Запити задаються об'єктами-фільтрами (`{ plan: "pro" }`) та операторами (`$gt`, `$in`, `$or`). Для складних перетворень існує **конвеєр агрегації** (`aggregate`): послідовність стадій (`$match`, `$group`, `$sort`, `$lookup`). Без індексу запит змушений переглядати всю колекцію; типи індексів: одиночні, складені, за масивами, текстові, геопросторові, TTL (автоматичне видалення за часом).

## 6. Транзакції та узгодженість

Операції над **одним документом** атомарні, у тому числі зі вкладеними даними. Транзакції з кількох документів (ACID) з'явилися у версії 4.0 (2018, для наборів реплік) і 4.2 (для шардованих кластерів), але вони дорожчі, тому модель даних зазвичай проєктують так, щоб потреба в них була мінімальною. Рівень гарантій налаштовується параметрами **write concern** (скільки вузлів мають підтвердити запис) та **read concern**.

## 7. Масштабування та відмовостійкість

- **Набір реплік** (replica set): один головний вузол (primary) і кілька вторинних; при відмові головного автоматично обирається новий.
- **Шардинг:** горизонтальне розподілення колекції між вузлами за ключем шардування. Вибір цього ключа є одним із найважливіших рішень і його важко змінити.

## 8. Сфери застосування

- вебзастосунки з різнорідними даними, каталоги товарів, профілі користувачів;
- системи керування контентом;
- журнали подій, IoT-дані, часові ряди (спеціальні колекції);
- швидке прототипування завдяки відсутності жорсткої схеми.

## 9. Сильні сторони та обмеження

| Сильні сторони | Обмеження |
|---|---|
| Гнучка модель, близька до об'єктів у коді | Складні зв'язки між даними незручні (`$lookup` повільніший за `JOIN`) |
| Природна відповідність JSON у JavaScript | Дублювання даних при вбудовуванні |
| Горизонтальне масштабування | Узгодженість переходить на застосунок |
| Потужний конвеєр агрегації | Ліцензія SSPL |

## 10. Поширені хибні уявлення

1. «У MongoDB немає схеми». Схема є, але неявна або задається валідацією; її відсутність у застосунку призводить до хаосу в даних.
2. «MongoDB не підтримує транзакцій». Підтримує з версії 4.0, хоча однодокументних операцій зазвичай досить.
3. «NoSQL означає відсутність з'єднань». Оператор `$lookup` виконує аналог `JOIN`, хоча і з іншими витратами.
4. «MongoDB зберігає JSON». Зберігається BSON з додатковими типами.
