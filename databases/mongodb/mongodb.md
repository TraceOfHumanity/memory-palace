# MongoDB: загальна характеристика

Усі приклади команд і виводи нижче перевірено реальними запусками: **MongoDB 8.2.3** (`mongod`) і **mongosh 2.5.10** на macOS, окремий тимчасовий сервер без автентифікації. Позначка **[довідково]** означає твердження з документації, яке в цих запусках не перевірялось. Дані в прикладах англійською, пояснення українською.

## Ключові відомості

## 1. Історичний контекст

MongoDB розроблено компанією 10gen, заснованою 2007 року Двайтом Мерріменом, Еліотом Горовицем і Кевіном Раяном; перший випуск СКБД відбувся 2009 року. Назва походить від англійського *humongous* («велетенський»). Компанію перейменовано на MongoDB, Inc. 2013 року. Поява системи пов'язана з рухом **NoSQL**, що виник як відповідь на потребу в горизонтальному масштабуванні та гнучкій схемі для вебзастосунків. 2018 року ліцензію змінено з AGPL на SSPL, яку Open Source Initiative не визнає відкритою; це варто враховувати при виборі.

## 2. Модель даних

Основна одиниця — **документ**: впорядкований набір пар «ключ-значення», що зберігається у форматі **BSON** (бінарний JSON). BSON додає до JSON типи, яких у ньому немає: `ObjectId`, `Date`, `Decimal128`, `Int32`, `Int64`, бінарні дані. Документи групуються в **колекції** (аналог таблиць), а колекції — у бази даних.

Кожен документ має унікальне поле `_id`; якщо його не задано, генерується `ObjectId` (12 байтів). Максимальний розмір документа — 16 МіБ. Документи можуть бути **вкладеними** й містити масиви, тому пов'язані дані часто зберігають разом в одному документі.

```js
db.users.insertOne({ email: "a@example.com", plan: "pro", tags: ["admin", "beta"] })

db.users.find({ plan: "pro" })

db.users.aggregate([
  { $group: { _id: "$plan", total: { $sum: 1 } } }
])
```

Порядок полів у документі **зберігається** (виміряно: `{ z: 1, a: 2, m: 3 }` повернувся як `_id, z, a, m`).

## 3. Типи даних

Документ зберігається в **BSON**, тому типів більше, ніж у JSON. Кожен тип має назву-псевдонім і числовий код; за ними працює оператор `$type`. Тип значення в запиті можна дізнатися через агрегацію:

```js
db.t.aggregate([{ $project: { _id: 0, t: { $type: "$field" } } }])
```

Усі типи, які вдалося зберегти й перевірити (виміряно командою `$type`):

| Значення в mongosh | Псевдонім `$type` | Код |
|---|---|---|
| `"text"` | `string` | 2 |
| `true` | `bool` | 8 |
| `NumberInt(55)` | `int` | 16 |
| `Long("10000000000")` | `long` | 18 |
| `Double(3.14)` | `double` | 1 |
| `Decimal128("123.456")` | `decimal` | 19 |
| `ISODate("2025-01-01T00:00:00Z")` | `date` | 9 |
| `Timestamp(1715395200, 1)` | `timestamp` | 17 |
| `ObjectId("507f1f77bcf86cd799439011")` | `objectId` | 7 |
| `null` | `null` | 10 |
| `[1, 2, 3]` | `array` | 4 |
| `{ name: "John" }` | `object` | 3 |
| `/^a.*z$/i` | `regex` | 11 |
| `BinData(0, "aGVsbG8=")`, `UUID("…")` | `binData` | 5 |
| `MinKey()` / `MaxKey()` | `minKey` / `maxKey` | -1 / 127 |
| `Code("function(){…}")` | `javascript` | 13 |

Коди й псевдоніми за таблицею: `$type: "int"` і `$type: 16` дали однаковий результат (виміряно).

### String — рядок

UTF-8 рядок. Будь-які мови й символи, довжина обмежена лише 16 МіБ розміру документа.

```js
db.users.insertOne({ name: "John" })
```

### Boolean — логічне значення

`true` або `false`. Псевдонім `$type`: `bool`.

```js
db.users.insertOne({ active: true })
```

### Числа: int, long, double, decimal

У BSON чотири числові типи; це найтонша частина MongoDB.

**Int32** (`int`, 4 байти) — цілі від -2 147 483 648 до 2 147 483 647. Створюється `NumberInt(55)`.

**Int64** (`long`, 8 байтів) — цілі до ±9 223 372 036 854 775 807. Створюється `Long("10000000000")` (або `NumberLong("10000000000")`). Передавати значення краще **рядком**: `NumberLong(5)` із числом дає попередження про можливу втрату точності.

**Double** (`double`, 8 байтів) — число з рухомою комою IEEE 754; зберігає дроби, але з похибкою. Створюється `Double(3.14)`.

**Decimal128** (`decimal`, 16 байтів) — точне десяткове число (34 значущі цифри). Для грошей і всього, де не можна втрачати копійки. Створюється `Decimal128("123.456")` або `NumberDecimal("123.456")`.

Що робить **mongosh** зі звичайним числовим літералом (виміряно):

| Літерал | Збережений тип |
|---|---|
| `55`, `2147483647`, `-2147483648` | `int` |
| `1.0` | `int` (ціле значення стає `int`) |
| `0.5`, `1.5` | `double` |
| `2147483648`, `10000000000`, `1e10`, `1e20` | **`double`**, а не `long` |
| `Double(5)` | `double` |
| `Long("5")` | `long` |

Тобто звичайне ціле, що не вміщується в Int32, потрапляє в базу як `double`. Якщо потрібен саме `long` — пишіть `Long("…")`.

Пастки:

- **Переповнення `NumberInt` мовчки «обертається»**: `NumberInt("3000000000")` дає `-1294967296`, а `NumberInt(2147483648)` — `-2147483648`. Помилки немає.
- Додавання двох `int` за межею Int32 в агрегації автоматично піднімає результат до `long`: `{ $add: [NumberInt(2147483647), NumberInt(1)] }` → `2147483648`.
- Дроби: `0.1 + 0.2` як `double` дає `0.30000000000000004`, а `{ $add: [Decimal128("0.1"), Decimal128("0.2")] }` дає точне `0.3` (виміряно).
- У JavaScript звичайні числа безпечні лише до 2⁵³: `9007199254740993` перетворюється на `9007199254740992`, а `Long("9007199254740993")` зберігає значення точно.

Перевірка «це число?» незалежно від виду: `{ $type: "number" }` (збігається з `int`, `long`, `double`, `decimal`) або в агрегації `{ $isNumber: "$field" }`.

### Date — дата й час

64-бітне число мілісекунд від 1970-01-01 UTC. У mongosh створюється `ISODate("2025-01-01T00:00:00Z")` або `new Date()`. Повертається як JavaScript `Date`.

```js
db.events.insertOne({ createdAt: new Date() })
db.events.insertOne({ day: ISODate("2025-01-01") })
```

Часового поясу тип не зберігає (завжди UTC). Діапазон у mongosh: від `0001-01-01` до `+275760-09-13`. Оператор оновлення `$currentDate` записує тип `Date`.

### Timestamp — внутрішня мітка

Пара «32-бітні секунди + 32-бітний порядковий номер»: `Timestamp(1715395200, 1)` → поля `t = 1715395200`, `i = 1`. Використовується всередині MongoDB (наприклад, журнал операцій). **Не плутайте з `Date`:** для часу подій у застосунку користуйтесь `Date`. Якщо вставити `Timestamp(0, 0)` у поле верхнього рівня, сервер сам підставить поточний час (виміряно: `t > 0`).

### ObjectId

12-байтовий ідентифікатор, який MongoDB генерує для `_id`, якщо ви його не задали. Записується як 24 шістнадцяткові цифри. Структура (виміряно на `507f1f77bcf86cd799439011`):

| Частина | Байти | Приклад | Сенс |
|---|---|---|---|
| Часова мітка | 4 | `507f1f77` = 1350508407 | секунди від епохи (2012-10-17T21:13:27Z) |
| Випадкове значення | 5 | `bcf86cd799` | унікальне для процесу |
| Лічильник | 3 | `439011` | зростає в межах процесу |

Властивості:

- Дві послідовні `new ObjectId()` мають однаковий початок (та сама секунда) і зростають: перша менша за другу (виміряно).
- З нього можна дістати час створення: `oid.getTimestamp()` → `2012-10-17T21:13:27.000Z`.
- У mongosh використовуйте `oid.toString()` або `oid.toHexString()` (24 символи). Поле `oid.str` з довідників для старої оболонки **не існує** (виміряно: `undefined`).
- Порядок за `_id` приблизно збігається з порядком створення.

```js
db.users.insertOne({ _id: ObjectId("507f1f77bcf86cd799439011"), name: "John" })
db.users.findOne({ _id: ObjectId("507f1f77bcf86cd799439011") })
```

Пошук за `_id` вимагає саме `ObjectId("…")`, а не рядка: рядок `"507f1f77…"` — інше значення.

### `_id` взагалі

Може бути значенням будь-якого типу, крім масиву. Виміряно: `_id: "abc"`, `_id: 5`, `_id: { a: 1, b: 2 }` збережено; `_id: [1, 2]` дало помилку `The '_id' value cannot be of type array`. Поле `_id` завжди індексоване й унікальне. Рядкові UUID як `_id` теж допустимі (`_id: "746c379f-5c0e-4069-8360-9bc75d2a2df9"`).

### Null і відсутнє поле

`null` — окремий тип. Виміряно:

| Запит | Збігається з |
|---|---|
| `{ n: null }` | полем `n` зі значенням `null` **і** документами **без** поля `n` |
| `{ n: { $exists: false } }` | лише документами без поля |
| `{ n: { $type: "null" } }` | лише полем зі значенням `null` |

Тому `{ field: null }` ловить і «порожнє», і «відсутнє»; якщо потрібно розрізняти — використовуйте `$exists` або `$type`. Значення `undefined` у mongosh зберігається як `null` (виміряно). `$type` для відсутнього поля в агрегації дає `"missing"`.

### Array — масив

Впорядкований список значень будь-яких типів, у тому числі змішаних і вкладених: `[1, "a", true, null, { x: 1 }, [2, 3]]` збережено без змін (виміряно).

```js
db.users.insertOne({ name: "Jane", tags: ["admin", "beta"] })
db.users.find({ tags: "beta" })        // містить елемент
db.users.find({ tags: { $size: 2 } })  // рівно 2 елементи
```

Запити за масивом шукають збіг з **будь-яким** елементом; багаторівневі масиви й оператори `$all`, `$elemMatch` описані в розділі з командами.

### Embedded Document — вкладений документ

Документ усередині документа (тип `object`). Доступ через **крапкову нотацію**.

```js
db.users.insertOne({ name: "Ann", address: { street: "Main", zip: "01001" } })
db.users.find({ "address.zip": "01001" })
```

Глибина вкладення на запити не впливає: `{ "a.b.c.d": 1 }` знайшов документ `{ a: { b: { c: { d: 1 } } } }` (виміряно). Не плутайте з рядком-ключем, у якому є крапка: `insertOne({ "a.b": 1 })` проходить, але запит `{ "a.b": 1 }` шукає вкладений шлях `a → b` і **не знаходить** такий документ (виміряно). Уникайте крапок і `$` на початку в іменах полів.

### BinData і UUID

`BinData(subtype, base64)` — довільні байти; підтип `0` — загальні бінарні дані (виміряно: `BinData(0, "aGVsbG8=")` повертає байти `hello`). `UUID("123e4567-e89b-12d3-a456-426614174000")` зберігається як `BinData` підтипу `4` (16 байтів). Компактніший за рядок із 36 символів.

### Regular Expression

Регулярний вираз зберігається як значення: `/^a.*z$/i`. Найчастіше використовується у запитах: `{ name: { $regex: /^j/i } }`.

### MinKey, MaxKey, JavaScript

`MinKey()` менший за будь-яке значення, `MaxKey()` більший за будь-яке — службові значення порівняння. Тип `javascript` (`Code(...)`) зберігає код функції як рядок; у новому коді зберігання коду не рекомендується. Застарілі типи (`undefined`, `symbol`, `dbPointer`, `javascriptWithScope`) не використовуйте **[довідково]**.

### Порядок типів при порівнянні та сортуванні

Якщо в одному полі лежать значення різних типів, `sort` упорядковує їх за типом **[довідково]**: MinKey → Null → числа → рядки → об'єкти → масиви → BinData → ObjectId → Boolean → Date → Timestamp → Regex → MaxKey. Виміряне сортування за зростанням: `MinKey`, `null`, `[1]` і `5` (масив порівнюється за своїм найменшим елементом), `"str"`, `{ a: 1 }`, `ObjectId`, `true`, `Date`, `Timestamp`, регулярний вираз, `MaxKey`.

### Розмір документа

Ліміт — **16 МіБ** (16 777 216 байт). `bsonsize({ a: 1 })` → `12` байтів, `bsonsize({ a: "hello" })` → `18`. Спроба зберегти документ із рядком у 17 МіБ відхилена на боці mongosh (помилка серіалізації, документ не вставлено).

### Перетворення типів

У конвеєрі агрегації (виміряно):

```js
db.t.aggregate([{ $project: { _id: 0,
  a: { $toString: "$i32" },                                       // "55"
  b: { $toInt: "12" },                                            // 12
  c: { $toDate: NumberLong(0) },                                  // 1970-01-01T00:00:00Z
  e: { $toDouble: "1.5" },                                        // 1.5
  g: { $toBool: 1 },                                              // true
  h: { $toDecimal: "0.1" },                                       // Decimal128("0.1")
  i: { $toObjectId: "507f1f77bcf86cd799439011" },                 // ObjectId(...)
  f: { $convert: { input: "abc", to: "int", onError: -1 } }       // -1
} }])
```

`$toDate` приймає `long` і `double`, але не `int` (з `int` отримано помилку `Unsupported conversion from int to date`). `$convert` без `onError` на непридатному значенні кидає помилку; з `onError` повертає заміну.

### Типи й валідація схеми

Тип можна вимагати через `$jsonSchema` (в ньому використовується `bsonType`). Виміряно для правила «обов'язковий рядковий `email`, `age` — `int` ≥ 0»:

| Документ | Результат |
|---|---|
| `{ age: 5 }` | відхилено (немає `email`) |
| `{ email: "a@b.c", age: NumberInt(5) }` | вставлено |
| `{ email: "a@b.c", age: 5.5 }` | відхилено (не `int`) |
| `{ email: "a@b.c", age: -1 }` | відхилено (`minimum: 0`) |
| `{ email: "a@b.c", age: 7 }` | вставлено (mongosh зберіг `7` як `int`) |

## 4. Проєктування даних: вбудовування чи посилання

Ключове рішення в MongoDB — як подавати зв'язки:

- **Вбудовування (embedding).** Пов'язані дані лежать у тому самому документі (наприклад, адреси користувача). Читання швидке (один запит), оновлення документа атомарне; але документ росте, а дані можуть дублюватися.
- **Посилання (referencing).** Документи посилаються один на одного через ідентифікатори (як зовнішні ключі); потрібен додатковий запит або операція `$lookup` (аналог `JOIN`).

Правило: вбудовуйте те, що читається разом і має обмежений розмір; посилайтеся на дані, що використовуються окремо або необмежено ростуть.

## 5. Схема

Схема **гнучка**: документи в одній колекції можуть мати різні поля. Це прискорює розробку, але відповідальність за узгодженість переходить до застосунку. Гнучкість не означає відсутність структури: MongoDB підтримує **валідацію схеми** (`$jsonSchema`), що змушує документи відповідати заданим правилам, а бібліотеки на кшталт Mongoose додають схеми на рівні застосунку. Приклад валідації див. у розділі 3 і в команді `createCollection` (розділ 13).

## 6. Запити та індекси

Запити задаються об'єктами-фільтрами (`{ plan: "pro" }`) та операторами (`$gt`, `$in`, `$or`). Для складних перетворень існує **конвеєр агрегації** (`aggregate`): послідовність стадій (`$match`, `$group`, `$sort`, `$lookup`). Без індексу запит змушений переглядати всю колекцію; типи індексів: одиночні, складені, за масивами, текстові, геопросторові, TTL (автоматичне видалення за часом). Команди запитів, індексів і агрегації з прикладами — у розділі 13.

## 7. Транзакції та узгодженість

Операції над **одним документом** атомарні, у тому числі зі вкладеними даними. Транзакції з кількох документів (ACID) з'явилися у версії 4.0 (2018, для наборів реплік) і 4.2 (для шардованих кластерів), але вони дорожчі, тому модель даних зазвичай проєктують так, щоб потреба в них була мінімальною. Рівень гарантій налаштовується параметрами **write concern** (скільки вузлів мають підтвердити запис) та **read concern**. Виміряно: на одиночному `mongod` (не набір реплік) спроба транзакції дала помилку `Transaction numbers are only allowed on a replica set member or mongos`.

## 8. Масштабування та відмовостійкість

- **Набір реплік** (replica set): один головний вузол (primary) і кілька вторинних; при відмові головного автоматично обирається новий.
- **Шардинг:** горизонтальне розподілення колекції між вузлами за ключем шардування. Вибір цього ключа є одним із найважливіших рішень і його важко змінити.

## 9. Сфери застосування

- вебзастосунки з різнорідними даними, каталоги товарів, профілі користувачів;
- системи керування контентом;
- журнали подій, IoT-дані, часові ряди (спеціальні колекції);
- швидке прототипування завдяки відсутності жорсткої схеми.

## 10. Сильні сторони та обмеження

| Сильні сторони | Обмеження |
|---|---|
| Гнучка модель, близька до об'єктів у коді | Складні зв'язки між даними незручні (`$lookup` повільніший за `JOIN`) |
| Природна відповідність JSON у JavaScript | Дублювання даних при вбудовуванні |
| Горизонтальне масштабування | Узгодженість переходить на застосунок |
| Потужний конвеєр агрегації | Ліцензія SSPL |

## 11. Поширені хибні уявлення

1. «У MongoDB немає схеми». Схема є, але неявна або задається валідацією; її відсутність у застосунку призводить до хаосу в даних.
2. «MongoDB не підтримує транзакцій». Підтримує з версії 4.0, хоча однодокументних операцій зазвичай досить.
3. «NoSQL означає відсутність з'єднань». Оператор `$lookup` виконує аналог `JOIN`, хоча і з іншими витратами.
4. «MongoDB зберігає JSON». Зберігається BSON з додатковими типами.

## 12. Запуск сервера й підключення

### mongod — запуск сервера

Сервер — процес `mongod`. Мінімально треба вказати каталог даних (`--dbpath`); журнал зручно писати у файл (`--logpath`).

```bash
mongod --dbpath /Users/alex/development/mongodb/data --logpath /Users/alex/development/mongodb/logs/mongodb.log
```

Додатково: `--port 27017` (порт за замовчуванням), `--bind_ip 127.0.0.1` (слухати лише локально). Виміряно: прапорець `--fork` на macOS **не працює** (`Server fork+exec via --fork … is incompatible with macOS`), тому сервер запускають у фоні засобами оболонки (`nohup … &`) або як службу. Сервер без `--auth` не вимагає пароля: лише для розробки.

### mongosh — підключення

```bash
mongosh                                     # localhost:27017
mongosh --port 27099                        # інший порт
mongosh "mongodb://127.0.0.1:27017/shop"    # рядок підключення, одразу база shop
mongosh --quiet --eval 'db.getName()'       # виконати вираз і вийти
mongosh --file script.js                    # виконати скрипт
```

Усередині скрипта (`--file`) команди оболонки на кшталт `use` і `show` не працюють як рядки; їх замінюють `use('shop')` (функція) і `db.getCollectionNames()`. Виміряно: `use shop3; db.users…` в одному `--eval` не виконується, бо весь рядок сприймається як назва бази.

## 13. Основні команди

Скрізь `db` — поточна база, `<collection>` — назва колекції (`db.users`). Виведення подано так, як його друкує mongosh. Умовні позначки: `<query>` — фільтр, `<document>` — документ, `<update>` — опис змін.

### Допомога

```js
help()                   // довідка по оболонці
db.help()                // методи бази
db.users.help()          // методи колекції
```

### show dbs

Показати всі бази даних із розмірами. База з'являється в списку лише тоді, коли в ній є дані.

```js
show dbs
```

```
admin    100.00 KiB
config    12.00 KiB
local     40.00 KiB
shop       8.00 KiB
```

Виміряно: до першого запису нова база в цьому списку відсутня.

### use `<database>`

Вибрати базу даних; якщо її немає, вона буде створена при першому записі.

```js
use shop
```

```
switched to db shop
```

Із функціонального коду (скрипти, `--file`) — `use('shop')`. Поточну базу показує `db.getName()` або просто `db`.

### show collections

Показати колекції поточної бази.

```js
show collections
```

```
users
```

Те саме значення як масив: `db.getCollectionNames()` → `[ 'users' ]`.

### db.createCollection("`<name>`")

Явно створити колекцію. Зазвичай колекція створюється автоматично першим `insert`, але явне створення потрібне для опцій: обмеженої колекції (`capped`), часових рядів (`timeseries`), валідатора.

```js
db.createCollection("users")
// { ok: 1 }

db.createCollection("cap", { capped: true, size: 4096, max: 3 })
```

Виміряно для `capped` з `max: 3`: після п'яти вставок `i = 0…4` лишилися лише останні три (`2, 3, 4`) — найстаріші автоматично видаляються. З валідатором:

```js
db.createCollection("strict", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["email"],
    properties: { email: { bsonType: "string" }, age: { bsonType: "int", minimum: 0 } }
  } }
})
```

Колекція часових рядів: `db.createCollection("metrics", { timeseries: { timeField: "t", metaField: "m" } })` — `getCollectionInfos` показує `type: "timeseries"`.

### db.getCollectionInfos()

Метадані колекцій: тип (`collection`, `view`, `timeseries`) і опції (валідатор).

```js
db.getCollectionInfos({ name: "users" })
```

### db.`<collection>`.insertOne(`<document>`)

Додати один документ. Без `_id` сервер створює `ObjectId`.

```js
db.users.insertOne({ name: "John", age: 30 })
```

```
{
  acknowledged: true,
  insertedId: ObjectId('6af1d3328e3bb557dc55a77c')
}
```

### db.`<collection>`.insertMany(`<documents>`)

Додати кілька документів одним запитом.

```js
db.users.insertMany([{ name: "John", age: 30 }, { name: "Jane", age: 25 }])
```

```
{
  acknowledged: true,
  insertedIds: { '0': ObjectId('…'), '1': ObjectId('…') }
}
```

За замовчуванням вставка **впорядкована** (`ordered: true`) і зупиняється на першій помилці. Виміряно: при масиві з `_id: 1, 1, 2` вставився лише перший документ, решта пропущена з помилкою `E11000 duplicate key`. З `{ ordered: false }` сервер пробує всі: вставилися `_id: 1` і `_id: 2`, дублікат відхилено.

```js
db.users.insertMany(docs, { ordered: false })
```

### db.`<collection>`.find()

Знайти документи. Без параметрів повертає **всі** документи колекції. Повертає курсор (`Cursor`), а не масив.

```js
db.users.find()
```

mongosh друкує перші **20** документів і підказку `Type "it" for more`; команда `it` показує наступні (виміряно на 25 документах: 20 + 5).

### db.`<collection>`.find({`<query>`})

Знайти документи за умовою (фільтр — документ-приклад).

```js
db.users.find({ age: 30 })
```

```
[ { _id: ObjectId('…'), name: 'John', age: 30 } ]
```

Кілька полів у фільтрі діють як **І**: `db.users.find({ age: 30, city: "Kyiv" })`.

### Проєкція: які поля повернути

Другий аргумент `find` — проєкція: `1` — включити, `0` — виключити. `_id` повертається завжди, якщо не вказати `_id: 0`. Не змішуйте `1` і `0` в одній проєкції (виняток — `_id`).

```js
db.users.find({ age: 30 }, { _id: 0, name: 1, age: 1 })
// [ { name: 'John', age: 30 } ]

db.users.findOne({ name: "Ann" }, { address: 0, _id: 0 })
// усе, крім address і _id
```

Приклад із реальної колекції вправ — фільтр за масивом і проєкція:

```js
db.exercises.find(
  { physicalQualities: { $in: ["coordination", "power", "balance"] } },
  { _id: 1, name: 1, physicalQualities: 1 }
)
```

### Оператори порівняння: $eq, $ne, $gt, $gte, $lt, $lte, $in, $nin

```js
db.users.find({ age: { $gt: 26 } })              // більше
db.users.find({ age: { $gte: 30, $lte: 40 } })   // діапазон
db.users.find({ age: { $in: [25, 41] } })        // один із списку
db.users.find({ city: { $ne: "Kyiv" } })         // не дорівнює
```

Увага: `$ne` і `$nin` повертають **також документи, в яких поля немає взагалі** (виміряно: фільтр `{ city: { $nin: ["Kyiv"] } }` повернув і `John`, у якого `city` відсутнє).

### Логічні оператори: $and, $or, $nor, $not

```js
db.users.find({ $or: [{ city: "Lviv" }, { age: 25 }] })
db.users.find({ $and: [{ age: { $gte: 30 } }, { city: "Kyiv" }] })
db.users.find({ $nor: [{ a: 1 }, { b: 1 }] })        // жодна з умов
db.users.find({ age: { $not: { $gt: 10 } } })        // заперечення умови
```

`$and` потрібен лише тоді, коли в одного поля є кілька однакових операторів або порядок важливий; звичайний фільтр з кількома полями — вже «І».

### $exists і $type

```js
db.users.find({ address: { $exists: true } })    // поле є (навіть зі значенням null)
db.users.find({ age: { $type: "number" } })      // за типом: "int", "long", "double", "string"…
```

### $regex — пошук за шаблоном

```js
db.users.find({ name: { $regex: /^j/i } })   // ім'я починається на «j», без урахування регістру
```

Регулярний вираз із якорем `^` на початку може використати індекс, без якоря — ні.

### Масиви: $all, $size, $elemMatch

```js
db.users.find({ tags: "beta" })                   // масив містить значення
db.users.find({ tags: { $all: ["admin", "beta"] } })  // містить усі перелічені
db.users.find({ tags: { $size: 2 } })             // довжина рівно 2
db.orders.find({ items: { $elemMatch: { sku: "b", qty: { $gt: 5 } } } })  // ОДИН елемент задовольняє ВСІ умови
```

Без `$elemMatch` умови на масив документів можуть виконуватись **різними** елементами.

### Вкладені поля (крапкова нотація)

```js
db.users.find({ "address.zip": "01001" })
```

Шлях у лапках обов'язковий.

### $expr — порівняння полів між собою

```js
db.n.find({ $expr: { $gt: ["$a", "$b"] } })   // документи, де a більше за b
```

### sort, skip, limit

```js
db.users.find({}, { _id: 0, name: 1 }).sort({ age: -1, name: 1 }).skip(1).limit(2)
```

`sort`: `1` — за зростанням, `-1` — за спаданням. Порядок викликів у ланцюжку значення не має: сервер завжди виконує `sort` → `skip` → `limit`. `.limit(10)` обмежує кількість документів у результаті.

### .toArray()

Перетворює курсор на масив (усе завантажується в пам'ять, на великих вибірках обережно).

```js
db.users.find().toArray()
```

### .forEach(`<function>`)

Виконати функцію для кожного документа курсору.

```js
db.users.find({ age: { $lt: 35 } }).forEach(function (doc) { print(doc.name); })
```

Виміряно: `forEach` обійшов `John, Jane, Ann`. У mongosh можна й `console.log(doc.name)`.

### Ручний обхід курсору: hasNext, next

```js
const c = db.users.find({}, { _id: 0, name: 1 }).sort({ name: 1 })
while (c.hasNext()) print(c.next().name)
```

### .pretty()

Колись форматував вивід `find`. У **mongosh** вивід і так форматований, `.pretty()` існує лише для сумісності й нічого не змінює: виміряно, результат `find({ age: 30 }).pretty()` ідентичний `find({ age: 30 })`. Писати його непотрібно.

### db.`<collection>`.findOne({`<query>`})

Повертає **перший** знайдений документ (не курсор) або `null`.

```js
db.users.findOne({ age: 30 })
// { _id: ObjectId('…'), name: 'John', age: 30 }
```

### countDocuments, estimatedDocumentCount

```js
db.users.countDocuments({ city: "Kyiv" })   // точна кількість за умовою
db.users.estimatedDocumentCount()           // швидка оцінка всієї колекції (з метаданих)
```

`cursor.count()` застарів: mongosh друкує `cursor.count is deprecated` і радить ці два методи.

### distinct — унікальні значення

```js
db.users.distinct("city")
// [ 'Kyiv', 'Lviv' ]
```

### db.`<collection>`.updateOne({`<query>`}, {`<update>`})

Оновити **перший** документ, що відповідає умові. Другий аргумент обов'язково містить оператори оновлення (`$set` тощо): без них команда не оновить документ, а видасть помилку `Update document requires atomic operators` (виміряно для `updateOne` і `updateMany`).

```js
db.users.updateOne({ name: "John" }, { $set: { age: 31 } })
```

```
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 1,
  modifiedCount: 1,
  upsertedCount: 0
}
```

`matchedCount` — скільки знайдено, `modifiedCount` — скільки реально змінилось (якщо значення те саме — 0). Якщо нічого не знайдено, обидва 0 (виміряно). У прикладі з обліку вправ перший документ «без умови» позначався маркером для подальшого видалення:

```js
db.users.updateOne({}, { $set: { marker: "toDelete" } })
```

### Оператори оновлення

Ці оператори працюють у `updateOne`, `updateMany`, `findOneAndUpdate`. Кожен приклад виміряно.

**$set** — встановити (або додати) поле:

```js
db.users.updateOne({ name: "John" }, { $set: { age: 31, "meta.updated": true } })
// { name: 'John', age: 31, meta: { updated: true } }
```

**$unset** — видалити поле (значення в запиті не важливе, пишуть `""`):

```js
db.exercises.updateOne(
  { _id: "746c379f-5c0e-4069-8360-9bc75d2a2df9" },
  {
    $set: {
      name: "Basic stance",
      description: "Stand upright with your feet shoulder-width apart and your arms hanging relaxed along your torso."
    },
    $unset: { targetMuscles: "" }
  }
)
```

**$inc** — збільшити число (від'ємне значення зменшує): `{ $inc: { age: 1 } }` → з 25 стало 26.

**$mul** — помножити: `{ $mul: { age: 2 } }` → 26 стало 52.

**$min / $max** — записати, лише якщо нове значення менше / більше за наявне: `{ $min: { age: 10 }, $max: { score: 7 } }` → `age: 10`, `score: 7` (поле, якого не було, створюється).

**$rename** — перейменувати поле: `{ $rename: { score: "points" } }` → `points: 7`, поля `score` більше немає.

**$currentDate** — записати поточний час як `Date`: `{ $currentDate: { updatedAt: true } }`.

**$setOnInsert** — значення лише при вставці під час `upsert` (див. нижче): `{ $set: { age: 1 }, $setOnInsert: { role: "new" } }`.

Операції з масивами:

**$push** — додати в кінець; з `$each` — кілька елементів:

```js
db.users.updateOne({ name: "Jane" }, { $push: { tags: "vip" } })
// tags: [ 'admin', 'beta', 'vip' ]
db.users.updateOne({ name: "Jane" }, { $push: { tags: { $each: ["a", "b"] } } })
// tags: [ 'admin', 'beta', 'vip', 'a', 'b' ]
```

**$addToSet** — додати, лише якщо такого значення ще немає: `{ $addToSet: { tags: "admin" } }` масив не змінив.

**$pull** — видалити всі елементи, що відповідають значенню/умові: `{ $pull: { tags: "a" } }`.

**$pop** — видалити останній (`1`) або перший (`-1`) елемент: `{ $pop: { tags: 1 } }`, `{ $pop: { tags: -1 } }`.

**Позиційний оператор `$`** — оновити перший елемент масиву, що збігся з умовою в фільтрі:

```js
db.users.updateOne({ name: "Bob", tags: "beta" }, { $set: { "tags.$": "BETA" } })
// tags: [ 'BETA' ]
```

**`$[<id>]` з `arrayFilters`** — оновити всі елементи масиву, що задовольняють фільтр:

```js
db.orders.updateOne(
  { _id: 1 },
  { $set: { "items.$[i].qty": 10 } },
  { arrayFilters: [{ "i.qty": { $gt: 2 } }] }
)
// items: [ { sku: 'a', qty: 1 }, { sku: 'b', qty: 10 } ]
```

### upsert — «оновити або вставити»

Опція `{ upsert: true }`: якщо документ за умовою не знайдено, він створюється з полів фільтра та `$set`.

```js
db.users.updateOne({ name: "Zed" }, { $set: { age: 50 } }, { upsert: true })
```

```
{
  acknowledged: true,
  insertedId: ObjectId('…'),
  matchedCount: 0,
  modifiedCount: 0,
  upsertedCount: 1
}
```

### Оновлення через конвеєр

Другим аргументом можна передати масив стадій — тоді нове значення обчислюється з наявних полів:

```js
db.users.updateOne({ name: "Robert" }, [{ $set: { age2: { $add: ["$age", 1] } } }])
```

### db.`<collection>`.updateMany({`<query>`}, {`<update>`})

Оновити **всі** документи, що відповідають умові. Результат має ту саму форму, що й `updateOne`.

```js
db.users.updateMany({ city: "Kyiv" }, { $set: { country: "UA" } })
// matchedCount: 2, modifiedCount: 2
```

### db.`<collection>`.replaceOne({`<query>`}, `<document>`)

Замінити **весь** документ (крім `_id`) новим. Другий аргумент — звичайний документ, **без** операторів.

```js
db.users.replaceOne({ name: "Bob" }, { name: "Robert", age: 42 })
// знайдено 1, змінено 1; тепер документ: { name: 'Robert', age: 42 } — поля city, tags зникли
```

Виміряно дві важливі речі:

- Оператор у заміні — помилка: `replaceOne(filter, { $set: { age: 1 } })` → `Replacement document must not contain atomic operators`. Щоб змінити лише поле, потрібен `updateOne`.
- **`replaceMany` не існує.** Виклик `db.users.replaceMany(...)` дає `TypeError: db.users.replaceMany is not a function`. (Звертання `db.users.replaceMany` без дужок повертає об'єкт, бо mongosh сприймає невідому властивість як вкладену колекцію.) Замінювати багато документів повністю — це `updateMany` з оператором або `bulkWrite`.

Старий метод `update` у mongosh існує (`typeof` → `function`), але застарілий; користуйтесь `updateOne`/`updateMany`.

### findOneAndUpdate, findOneAndReplace, findOneAndDelete

Атомарно змінюють документ **і повертають його** — корисно для лічильників і черг. За замовчуванням повертають документ **до** зміни; `returnDocument: "after"` — після.

```js
db.users.findOneAndUpdate(
  { name: "Robert" },
  { $inc: { age: 1 } },
  { returnDocument: "after", projection: { _id: 0, name: 1, age: 1 } }
)
// { name: 'Robert', age: 43 }

db.users.findOneAndUpdate({ name: "Robert" }, { $inc: { age: 1 } }, { projection: { _id: 0, age: 1 } })
// { age: 43 }   ← значення до збільшення (стало 44)

db.users.findOneAndDelete({ name: "Zed" }, { projection: { _id: 0, name: 1 } })
// { name: 'Zed' }

db.users.findOneAndReplace({ name: "Neo" }, { name: "Neo", age: 2 }, { returnDocument: "after" })
```

### db.`<collection>`.deleteOne({`<query>`})

Видалити **перший** документ за умовою.

```js
db.users.deleteOne({ age: 30 })
db.exercises.deleteOne({ _id: ObjectId("69259210f204daec772efeff") })
```

```
{ acknowledged: true, deletedCount: 1 }
```

### db.`<collection>`.deleteMany({`<query>`})

Видалити **всі** документи за умовою.

```js
db.users.deleteMany({ age: 30 })
db.users.deleteMany({ marker: "toDelete" })
// { acknowledged: true, deletedCount: 2 }
```

### db.`<collection>`.deleteMany({})

Порожній фільтр видаляє **всі** документи колекції, але сама колекція та її **індекси лишаються**. Виміряно: після створення індексу `i_1` і `deleteMany({})` кількість індексів так і лишилась 2 (`_id_` і `i_1`).

```js
db.users.deleteMany({})
```

Небезпечно: немає запиту підтвердження. Перед масовим видаленням перевірте фільтр через `find` або `countDocuments`.

### db.`<collection>`.drop()

Видалити колекцію **разом з усіма документами та індексами**.

```js
db.users.drop()
// true
```

Виміряно: повторний `drop` вже неіснуючої колекції на цьому сервері також повернув `true`.

### db.`<collection>`.renameCollection("`<new>`")

```js
db.users.renameCollection("people")
```

### bulkWrite — кілька різних операцій одним запитом

```js
db.users.bulkWrite([
  { insertOne: { document: { name: "B1" } } },
  { updateOne: { filter: { name: "B1" }, update: { $set: { x: 1 } } } },
  { deleteOne: { filter: { name: "Neo" } } }
])
// вставлено 1, змінено 1, видалено 1
```

Менше мережевих запитів, ніж при окремих викликах.

### Індекси: createIndex, getIndexes, dropIndex

Індекс прискорює пошук і сортування, але сповільнює запис і займає місце.

```js
db.users.createIndex({ age: 1 })                  // одиночний → "age_1"
db.users.createIndex({ city: 1, age: -1 })        // складений → "city_1_age_-1"
db.users.createIndex({ name: 1 }, { unique: true }) // унікальний → "name_1"
db.users.getIndexes()                             // список; завжди є _id_
db.users.dropIndex("age_1")                       // видалити за назвою
```

Виміряно: вставка документа з уже наявним `name` при унікальному індексі → `E11000 duplicate key error`. Інші види:

```js
db.users.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })  // TTL: документ видалиться через годину
db.articles.createIndex({ title: "text" })                           // текстовий
db.articles.find({ $text: { $search: "mongodb" } })                  // → [ { title: 'MongoDB basics' } ]
```

### explain — як виконується запит

```js
db.logs.find({ k: 2 }).explain().queryPlanner.winningPlan.stage
```

Виміряно: без індексу плановий вузол — `COLLSCAN` (повний перегляд колекції), після `createIndex({ k: 1 })` — `FETCH` над `IXSCAN` (використано індекс). Із `explain("executionStats")` видно, скільки документів і ключів переглянуто (`totalDocsExamined`, `totalKeysExamined`): для запиту, що повернув 3 документи за індексом, переглянуто 3 ключі й 3 документи.

### aggregate — конвеєр агрегації

Послідовність стадій; результат кожної є входом наступної.

```js
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$user", sum: { $sum: "$total" }, n: { $sum: 1 } } },
  { $sort: { _id: 1 } }
])
// [ { _id: 'Ann', sum: 100, n: 1 }, { _id: 'Bob', sum: 70, n: 1 } ]
```

Основні стадії (виміряно):

```js
{ $addFields: { withTax: { $multiply: ["$total", 1.2] } } }    // нове поле (60, 120)
{ $project: { _id: 0, user: 1, withTax: 1 } }                  // вибрати поля
{ $limit: 2 }                                                  // обмежити
{ $unwind: "$tags" }                                           // кожен елемент масиву → окремий документ
{ $count: "n" }                                                // кількість → [ { n: 3 } ]
{ $group: { _id: null, avg: { $avg: "$age" }, max: { $max: "$age" } } }  // avg: 36.2, max: 50
{ $lookup: { from: "users", localField: "user", foreignField: "name", as: "u" } }  // аналог JOIN
```

`$lookup` додає масив `u` з відповідними документами іншої колекції (виміряно: для замовлення Ann знайдено місто `Kyiv`).

### db.stats()

Статистика бази: кількість колекцій, документів, розміри даних та індексів.

Поля (виміряно): `db`, `collections`, `views`, `objects`, `avgObjSize`, `dataSize`, `storageSize`, `indexes`, `indexSize`, `totalSize`, `scaleFactor`, `fsUsedSize`. Для колекції — `db.users.stats()` (`count`, `size`, `capped`, `wiredTiger`, …).

## 14. Типові помилки

1. Забути, що `find` повертає курсор: для масиву потрібен `.toArray()`, для одного документа — `findOne`.
2. `updateOne` без оператора (`updateOne(filter, { age: 31 })`) — помилка; потрібен `$set`.
3. Шукати за `_id` рядком замість `ObjectId("…")`.
4. `replaceOne` із `$set` — помилка; `replaceMany` не існує.
5. `deleteMany({})` замість `drop()` (залишаються індекси) і навпаки.
6. `{ field: null }` вважати «поле порожнє»: збігається і з відсутнім полем.
7. `$ne`/`$nin` повертають документи без поля.
8. Очікувати `long` від великого цілого в mongosh (виходить `double`); `NumberInt` мовчки обертається при переповненні.
9. Гроші зберігати в `double` (потрібен `Decimal128`).
10. Умови на масив документів без `$elemMatch`.
11. Крапка або `$` у назві поля.
12. Масивне зростання вбудованого масиву — документ впирається в 16 МіБ.
13. Запит без індексу на великій колекції (`COLLSCAN`); не перевіряти `explain`.
14. Покладатись на `.pretty()` і `cursor.count()` — застарілі.
15. Запускати `mongod --fork` на macOS.
16. Виконувати `deleteMany`/`drop` не в тій базі: завжди перевіряти `db`.

## 15. Алгоритм роботи

1. Запустити `mongod` з `--dbpath` і підключитись `mongosh`.
2. `use <database>` → `show collections`.
3. Вставити дані (`insertOne` / `insertMany`), якщо потрібно — з явним типом числа.
4. Читати: `find(filter, projection).sort().limit()`, одиничний — `findOne`.
5. Змінювати: `updateOne` / `updateMany` з `$set`, `$inc`, `$push` …; повна заміна — `replaceOne`.
6. Видаляти: `deleteOne` / `deleteMany`; колекцію — `drop()`.
7. Для швидкості — `createIndex`, перевірка через `explain`.
8. Для складних вибірок — `aggregate`.
9. Тип даних, що має значення (гроші, великі числа, дати), задавати явно (`Decimal128`, `Long`, `ISODate`) і за потреби закріпити через `$jsonSchema`.
