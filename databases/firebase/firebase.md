# Firebase: загальна характеристика

## Ключові відомості

| Параметр | Характеристика |
|---|---|
| Тип | платформа «бекенд як сервіс» (BaaS) з хмарними базами даних |
| Власник | Google (придбано 2014 року) |
| Бази даних | Cloud Firestore, Realtime Database |
| Модель даних | NoSQL: документи й колекції (Firestore), дерево JSON (Realtime Database) |
| Ключова особливість | синхронізація в реальному часі та робота офлайн |
| Розгортання | керований хмарний сервіс (Google Cloud), без власного сервера |
| Ліцензування | пропрієтарний сервіс; безкоштовний тариф Spark, оплата за використання (Blaze) |
| Основні клієнти | JavaScript (веб, Node.js), Android, iOS, Flutter та інші |

## 1. Що таке Firebase

Firebase — це не одна база даних, а **платформа розробки застосунків** («бекенд як сервіс», Backend-as-a-Service). Вона надає готові серверні можливості, щоб клієнтський застосунок (веб чи мобільний) міг працювати без власного бекенду. Склад платформи:

- **бази даних:** Cloud Firestore та Realtime Database;
- **Authentication** — реєстрація та вхід (пошта, Google, телефон тощо);
- **Cloud Functions** — серверний код, що запускається за подіями;
- **Cloud Storage** — зберігання файлів;
- **Hosting** — розміщення вебзастосунків;
- **Cloud Messaging** — push-сповіщення;
- також аналітика, віддалена конфігурація, перевірка автентичності застосунку.

## 2. Історичний контекст

Firebase виник 2011 року як стартап Джеймса Тамплина та Ендрю Лі, що розвинувся з сервісу чатів для сайтів; основним продуктом стала база даних реального часу (Realtime Database). У жовтні 2014 року компанію придбала Google, після чого платформа поступово інтегрувалася з Google Cloud. 2017 року з'явилася друга база — **Cloud Firestore** (загальну доступність оголошено 2019 року), розроблена як масштабованіша й функціональніша наступниця.

## 3. Дві бази даних

**Realtime Database.** Уся база — один великий **JSON-об'єкт** (дерево). Дані синхронізуються з клієнтами майже миттєво через постійне з'єднання. Проста модель, але складні запити та глибока вкладеність незручні.

**Cloud Firestore.** Дані організовано як **колекції** документів; документ містить поля й може мати **підколекції**. Підтримуються складніші запити, індекси, транзакції та пакетні записи. Обмеження розміру документа — 1 МіБ. Для нових проєктів Firebase зазвичай рекомендує саме Firestore.

```js
import { initializeApp } from "firebase/app";
import { getFirestore, collection, addDoc, onSnapshot } from "firebase/firestore";

const app = initializeApp({ /* конфігурація вашого проєкту Firebase */ });
const db = getFirestore(app);

await addDoc(collection(db, "notes"), { title: "Перша нотатка" });

// підписка на зміни в реальному часі
onSnapshot(collection(db, "notes"), (snapshot) => {
  snapshot.forEach((doc) => console.log(doc.id, doc.data()));
});
```

Цей код ілюструє модульний клієнтський SDK (версії 9 і новіші) і потребує реального проєкту Firebase, тому як самостійний скрипт не запускається.

## 4. Запити

Запити Firestore — це фільтри за полями, сортування та обмеження результату. Основні обмеження порівняно з SQL:

- **немає з'єднань (`JOIN`)**: пов'язані дані або дублюють, або вибирають окремими запитами;
- кожен запит має покриватися **індексом**; прості одиночні індекси створюються автоматично, складені створюють вручну;
- агрегації (кількість, сума) підтримуються, але набір операцій обмежений;
- запит вибирає лише з однієї колекції (або групи колекцій із тим самим ім'ям).

Проєктування даних тому виходить із **запитів**, а не з нормалізації: структуру підбирають під ті вибірки, які потрібні застосунку.

## 5. Реальний час та офлайн-режим

Клієнтські SDK надають **слухачів** (`onSnapshot`), які отримують нові дані щоразу, коли вони змінюються на сервері. Клієнт також підтримує **локальний кеш**: застосунок продовжує працювати без мережі, а зміни синхронізуються після відновлення зв'язку. Це основна причина вибору Firebase для мобільних і колаборативних застосунків.

## 6. Безпека: правила доступу

Клієнтський застосунок звертається до бази **безпосередньо**, тому захист будується не на сервері, а на **Security Rules** — декларативних правилах, що визначають, хто може читати й писати які документи (наприклад, за ідентифікатором автентифікованого користувача). Помилково відкриті правила (`allow read, write: if true`) — найчастіша причина витоків даних. Для серверного коду використовують **Admin SDK** (`firebase-admin`), який обходить правила й має повні права; його ключі не можна віддавати клієнту.

Локально систему можна розробляти й тестувати за допомогою **Firebase Emulator Suite**, не звертаючись до хмари.

## 7. Транзакції та узгодженість

Cloud Firestore забезпечує **сильну узгодженість** читання й підтримує транзакції та пакетні (batched) записи, що виконуються атомарно. Кількість записів в один документ обмежена (порядок одного запису на секунду в межах документа), тому для лічильників із високою частотою оновлень застосовують розподілені лічильники.

## 8. Сфери застосування

- мобільні й вебзастосунки з мінімальним власним бекендом;
- чати, спільні редактори, дашборди реального часу;
- швидкі прототипи та стартапи;
- застосунки, що мають працювати офлайн.

## 9. Сильні сторони та обмеження

| Сильні сторони | Обмеження |
|---|---|
| Готова інфраструктура, немає серверів | Прив'язка до постачальника (vendor lock-in) |
| Синхронізація в реальному часі, офлайн | Обмежені запити: немає `JOIN`, залежність від індексів |
| Інтегровані автентифікація, сховище, функції | Вартість зростає разом з кількістю операцій читання/запису |
| Автоматичне масштабування | Безпека повністю залежить від правил доступу |

## 10. Поширені хибні уявлення

1. «Firebase — це база даних». Це платформа, база даних є лише одним із її сервісів.
2. «Firebase не потребує проєктування даних». Через відсутність `JOIN` структуру даних доводиться проєктувати ретельніше, під запити.
3. «Клієнтський код можна не захищати, бо все на сервері». Саме тому правила безпеки критично важливі.
4. «Firebase завжди дешевий». Безкоштовний тариф обмежений, а вартість залежить від кількості операцій.
