# PostgreSQL: загальна характеристика

## Ключові відомості

| Параметр | Характеристика |
|---|---|
| Тип | об'єктно-реляційна система керування базами даних (СКБД) |
| Модель даних | реляційна: таблиці, рядки, зв'язки; розширена типами JSONB, масивами, діапазонами |
| Мова запитів | SQL (з розширеннями), процедурна мова PL/pgSQL |
| Витоки | проєкт POSTGRES, Каліфорнійський університет у Берклі, 1986 |
| Назва PostgreSQL | з 1996 року |
| Розробка | PostgreSQL Global Development Group (спільнота) |
| Ліцензія | PostgreSQL License (дозвільна, подібна до BSD/MIT) |
| Архітектура | клієнт-серверна; окремий процес на кожне з'єднання |
| Порт за замовчуванням | 5432 |
| Клієнт командного рядка | `psql` |

## 1. Історичний контекст

Витоки PostgreSQL сягають проєкту **POSTGRES**, який 1986 року в Каліфорнійському університеті в Берклі очолив Майкл Стоунбрейкер як наступника системи Ingres. Ідея полягала в розширюваній моделі даних: користувач може визначати власні типи, оператори й методи доступу. Мову SQL до системи додали 1994–1995 років (версія Postgres95), а 1996 року проєкт отримав нинішню назву **PostgreSQL** і перейшов під керування відкритої спільноти. Відтоді нова основна версія виходить приблизно раз на рік.

## 2. Модель даних

Дані зберігаються в **таблицях**, що складаються з рядків і типізованих стовпців. Цілісність забезпечують обмеження: первинні й зовнішні ключі, `UNIQUE`, `NOT NULL`, `CHECK`. Схема (структура таблиць) задається наперед і перевіряється сервером.

Відмінна риса PostgreSQL — багатство типів: цілі та дробові, `numeric` довільної точності, `text`, дата й час із часовим поясом, `uuid`, масиви, діапазони, мережеві адреси та **`jsonb`** — бінарний JSON з індексацією. Завдяки цьому одна СКБД поєднує реляційний і документо-орієнтований підходи. Користувач може створювати власні типи, оператори та розширення (наприклад, **PostGIS** для геоданих).

```sql
CREATE TABLE users (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text   NOT NULL UNIQUE,
    meta  jsonb  NOT NULL DEFAULT '{}'
);

INSERT INTO users (email, meta) VALUES ('a@example.com', '{"plan": "pro"}');

SELECT email FROM users WHERE meta->>'plan' = 'pro';
```

## 3. Архітектура

PostgreSQL використовує клієнт-серверну модель: головний процес приймає з'єднання й породжує **окремий процес** для кожного клієнта. Через це велика кількість одночасних з'єднань є дорогою, і в практиці застосовують пул з'єднань (наприклад, PgBouncer).

Надійність забезпечує **журнал випереджувального запису** (WAL, write-ahead log): зміни спершу записуються в журнал і лише потім у файли даних, що дозволяє відновити стан після збою. Обслуговування простору виконує процес **VACUUM** (див. розділ 5).

## 4. Запити та оптимізація

Запити пише мовою SQL, а **планувальник запитів** на основі статистики обирає найдешевший план виконання (`EXPLAIN` показує його). Підтримуються: з'єднання таблиць (`JOIN`), підзапити, загальні табличні вирази (`WITH`, зокрема рекурсивні), віконні функції, повнотекстовий пошук, партиціонування таблиць.

Індекси кількох типів: **B-tree** (за замовчуванням), Hash, GiST, SP-GiST, **GIN** (для `jsonb`, масивів, тексту), BRIN (для великих упорядкованих таблиць). Вибір індексу під характер запитів — головний інструмент продуктивності.

## 5. Транзакції та узгодженість

PostgreSQL відповідає властивостям **ACID** (атомарність, узгодженість, ізольованість, довговічність). Одночасний доступ реалізовано через **MVCC** (багатоверсійне керування паралелізмом): кожна транзакція бачить знімок даних, тому читачі не блокують письменників, а письменники читачів. Оновлення створює нову версію рядка, а старі версії видаляє процес VACUUM; його запобіжне налаштування (autovacuum) є важливою частиною експлуатації.

Рівні ізольованості: `Read Committed` (за замовчуванням), `Repeatable Read`, `Serializable`. Змінювати структуру таблиць (DDL) можна всередині транзакції з можливістю відкату, що для СКБД є нетиповою перевагою.

## 6. Масштабування та реплікація

- **Потокова (streaming) реплікація** створює копії для читання та резервування.
- **Логічна реплікація** передає окремі таблиці або зміни на рівні рядків.
- Вертикальне масштабування (потужніший сервер) є основним шляхом; горизонтальне (шардинг) потребує додаткових рішень (наприклад, Citus) і не є вбудованою можливістю.

## 7. Сфери застосування

- бекенд вебзастосунків, фінансові й облікові системи, де важлива цілісність;
- аналітика й звітність (віконні функції, складні запити);
- геоінформаційні системи (PostGIS);
- універсальне сховище для поєднання реляційних даних із JSON.

## 8. Сильні сторони та обмеження

| Сильні сторони | Обмеження |
|---|---|
| Повна підтримка ACID та MVCC | Модель «процес на з'єднання» потребує пулу |
| Розширюваність (типи, індекси, розширення) | Горизонтальне масштабування не вбудоване |
| Багатий SQL і JSONB | Потрібне налаштування та обслуговування (VACUUM) |
| Відкрита ліцензія, велика спільнота | Складніше адміністрування, ніж у вбудованих БД |

## 9. Поширені хибні уявлення

1. «Реляційні бази не масштабуються». Одна серверна PostgreSQL обробляє великі навантаження, а реплікація та партиціонування розширюють можливості.
2. «PostgreSQL — лише реляційна». Через `jsonb` вона добре працює з напівструктурованими даними.
3. «MVCC означає відсутність блокувань». Читання не блокує запису, але конфлікти записів усе одно керуються блокуваннями.
4. «VACUUM необов'язковий». Без нього таблиці «розпухають», а продуктивність падає.
